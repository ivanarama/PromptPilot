# ПРОТОТИП: Каскадный ревью + Портфель + Самолечение для PromptPilot

> Статус: НА УТВЕРЖДЕНИЕ. Исполнения нет — это спецификация интерфейса и
> механики. После твоих правок собираем живой прототип, обкатываем на одном
> этапе, затем — предложение автору (в дополнение к #88).

---

## 0. Резюме

Три функции, один дизайн-принцип: **движок агностичен к именам агентов** —
пользователь заполняет СЛОТЫ (кто исполнитель, кто ревьюер-1, кто
ревьюер-2/арбитр, кто планер), а механизм исполняет цепочку независимо от
того, какие модели в неё поставлены.

| Функция | Что даёт | Где живёт |
|---|---|---|
| **A. Каскадный ревью** | Ревью-1 (GLM) фильтрует, Ревью-2 (Qwen) арбитр; находки Ревью-2 чинит назначенный фиксер | Вкладка воркфлоу → новый блок «Каскад» в настройках этапа |
| **B. Портфель (надсмотрщик)** | Одна цель → N параллельных воркфлоу, визуальные потоки, поезд слияний | Новый экран «Портфели» рядом с Workflows |
| **C. Самолечение** | Верdict-repair (Jev/ядро #92), таймаут-авторезюме (лимит 2), авто-Продолжить при старте системы | Настройки → секция «Самолечение» |

Всё поверх существующего REST API: config PATCH, human-input, sync, events.
Ядро не меняем. Для автора потом — предложение сделать это нативным.

## 1. Функция A: Каскадный ревью

### 1.1 Как это работает (механика)

Конечный автомат фаз на одном раунде:

```
                    ┌──────────────────────────────────────────────┐
                    │            НЕ ИЗМЕНИЛОСЬ: гейт как был       │
                    ▼                                              │
[EXEC] исполнитель слота Э ──→ [GATE] ──→ [REV-1] слот Р1 ──┬──→ PASS ──→ [REV-2] слот Р2 ──┬──→ PASS ──→ этап закрыт
                    ▲                                       │                               │
                    │  REVISION (чинит слот Э)              │ REVISION (чинит слот Ф2)      │
                    └───────────────────────────────────────┘                               │
 Duke: находки Ревью-2 уходят ФИКСЕРУ слота Р2 (например GLM),                     │
 а не экзекьютору — эскалация ответственности                                       ▼
                                                                            лимит исчерпан →
                                                     политика: арбитраж планером / принять
                                                     при зелёном гейте / человеку
```

- Настройки хранятся в конфиге воркфлоу (опциональный ключ `review_chain`) —
  нет ключа = старое поведение одного ревьюера. Ничего не ломает.
- Переключение исполнителя между фазами — существующий config PATCH
  (действует с ближайшего диспетча, безопасно даже посреди раунда).
- Переход PASS Р1 → Р2: автомат ставит ревьюером слот 2 и делает
  human-input resume — Р2 видит дифф и вердикт Р1 в своём промпте.

### 1.2 Интерфейс: шаг «Команда» визаря (после включения каскада)

```
┌─ Шаг 2. Команда ────────────────────────────────────────────────────────┐
│                                                                          │
│  ПЛАНЕР      [ codex            ▼]  модель [gpt-5.6-luna]  effort [max▼] │
│                                                                          │
│  ИСПОЛНИТЕЛЬ [ mmx-m3            ▼]  модель [—]            effort [max▼] │
│                                                                          │
│  ── ЦЕПОЧКА РЕВЮ ──────────────────────────────────  [+] Добавить ступень│
│                                                                          │
│  ┌─ Ступень 1 · Ревью-1 ──────────────────────────────── ⋮ (удалить) ──┐ │
│  │ Провайдер [ goose-zai        ▼]  Модель [—]   effort [max▼]        │ │
│  │ Находки чинит:  (•) исполнитель воркфлоу                           │ │
│  │                 ( ) этот же провайдер                              │ │
│  │                 ( ) указать: [ goозе-zai         ▼]                │ │
│  │ ☑ Блокирующий: PASS обязателен для перехода дальше                 │ │
│  │ Лимит раундов [2]   Исчерпан: [арбитраж планером        ▼]         │ │
│  └────────────────────────────────────────────────────────────────────┘ │
│  ┌─ Ступень 2 · Ревью-2 (арбитр) ─────────────────────── ⋮ (удалить) ──┐ │
│  │ Провайдер [ qwen-review      ▼]  Модель [—]   effort [max▼]        │ │
│  │ Находки чинит:  ( ) исполнитель воркфлоу                           │ │
│  │                 (•) этот же провайдер                              │ │
│  │ Лимит раундов [3]   Исчерпан: [арбитраж планером        ▼]         │ │
│  │ ⏰ Окно работы: [22:00] — [04:00] tz [Europe/Moscow▼]              │ │
│  │      ☐ вне окна слот пропускается (не блокирует)                   │ │
│  └────────────────────────────────────────────────────────────────────┘ │
│                                                                          │
│  ☑ КАСКАД ВКЛЮЧЁН (снять галочку → обычный один ревьюер)                │
└──────────────────────────────────────────────────────────────────────────┘
```

Принципы контролов (твоё требование «ничего в коде»):
- Провайдер/модель — **дропдауны** из providers.json (список уже есть в UI);
- Все режимы — **галочки и радио**: блокирующий/консультативный, кто чинит;
- Числа — маленькие поля с дефолтами;
- ⋮ — удалить ступень; [+] — добавить (до 3–4 ступеней, чтобы цитадель
  не превращалась в бесконечную бюрократию).

### 1.3 Что под капотом (без правок ядра)

```
config (JSON воркфлоу):
"review_chain": {
  "enabled": true,
  "steps": [
    {"slot": 1, "provider": "goose-zai",   "fixer": "executor",
     "blocking": true, "max_rounds": 2,
     "on_exhaust": "arbitrate_planner"},
    {"slot": 2, "provider": "qwen-review", "fixer": "self",
     "blocking": true, "max_rounds": 3,
     "on_exhaust": "arbitrate_planner",
     "window": {"from": "22:00", "to": "04:00", "tz": "Europe/Moscow",
                "outside": "skip"}}
  ],
  "final_approval": "planner"
}
```

Движок каскада (демон, тот же класс что вердикт-вотчер):
- слушает `review.awaiting_decision` / `review.revision_required`;
- по слоту: PASS → следующий слот (PATCH reviewer.provider + resume);
- REVISION → PATCH executor.provider = fixer слота + resume;
- лимиты считает сам; исчерпан → политика слота.

Для автора (натив, потом): это один цикл `for slot in chain` внутри
существующей фазы reviewing + карточки в визаре. Наш демон — референс.

## 2. Функция B: Портфель (надсмотрщик)

### 2.1 Экран «Портфели» (новая вкладка рядом с Workflows)

```
┌─ Портфели ────────────────────────────────────────── [+] Новый портфель ┐
│                                                                          │
│  ▾ Портфель: Экраны ФТ-5/6/10                        ┌──────────────┐  │
│    Цель: привязать экраны :app к модулям             │ ⏵ Запустить  │  │
│    База: main → Integration: integration/ft-5610     │ ⏸ Пауза      │  │
│    ┌────────────────┬─────────┬────────┬───────────┐ │ ⏹ Стоп       │  │
│    │ Пакет          │ Поток   │ Статус │ Гейт      │ └──────────────┘  │
│    ├────────────────┼─────────┼────────┼───────────┤                   │
│    │ dictionary-ui  │ ● goose │ ревью  │ ✓ green   │                   │
│    │ statistics-ui  │ ● mmx   │ выполн │ ✓ green   │                   │
│    │ catalog-wire   │ ● flash │ ожид.  │ —         │                   │
│    └────────────────┴─────────┴────────┴───────────┘                   │
│    Поезд слияний: 2/3 слито · гейт после слияния: ✓                     │
│    [Открыть карточки воркфлоу] [Открыть integration-ветку]              │
└──────────────────────────────────────────────────────────────────────────┘
```

- Каждый «поток» = обычный воркфлоу PromptPilot (карточки доступны как
  раньше — клик по строке открывает их); портфель — только координатор.
- Поезд слияний: серийный merge в integration-ветку + гейт после каждого;
  конфликт → пакет краснеет, едет на доработку, остальные не ждут.
- Ячейка «Поток» показывает провайдера пакета — видно, кто чем занят
  (твоя просьба «кто чем сейчас занимается» — уже реализованные чипы
  воркфлоу/роли в списке задач остаются и работают здесь же).

### 2.2 Модель портфеля (spec-файл, редактируемый и в UI)

```json
{
  "goal": "…",
  "base_branch": "main",
  "integration_branch": "integration/ft-5610",
  "merge_gate": ".\\gradlew.bat test :app:assembleDebug --no-daemon",
  "packages": [
    {"id": "dictionary-ui", "slug": "pkg-dict", "prompt": "…",
     "gate": ".\\gradlew.bat :feature:dictionary:test --no-daemon",
     "allowed_paths": ["feature/dictionary/**", "app/ui/dictionary/**"],
     "depends_on": []},
    {"id": "statistics-ui", "depends_on": ["dictionary-ui"], "…": "…"}
  ]
}
```

Зависимости: пакет стартуется, когда все `depends_on` слиты. Так задаются
и чисто параллельные пачки, и последовательные хвосты.

## 5. Потоки (как это живёт)

### Создание каскадного воркфлоу
Визарь шаг 2 → «Команда» → включил каскад → заполнил слоты → шаг 4
(гейты уже из слотов) → создать. Дальше автоматика: EXEC→GATE→REV-1→(REV-2)→…

### Создание портфеля
«Портфели» → Новый → вставил цель + пакеты (или сгенерировал планером —
кнопка «Нарезать планером», тот же decompose-вызов) → Запустить →
воркфлоу создаются сами, потоки поехали.

### Отказы
- Потеря вердикта → вердикт-репэйр (#92 в ядре / внешний вотчер) → раунд
  продолжен; лог.
- Таймаут → авторезюме (≤2) → эскалация в ТГ.
- Провайдер мёртв → эскалация сразу.
- Петля ревизий → политика исчерпания (арбитраж/принять при зелёном гейте).
