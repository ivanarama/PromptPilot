# Явные команды проверок

Новые проверки можно задавать объектом вместо shell-строки:

```json
{"argv":["python","tests/check.py"],"inputs":["tests/check.py"],"repeat":"per-attempt"}
```

`argv` передаётся процессу без промежуточной оболочки. `inputs` перечисляет
точные относительные POSIX-пути существующих обычных файлов репозитория;
для проверки этапа эти пути должны входить в его `deliverables`. Системный
интерпретатор должен быть установлен заранее. Исполняемый файл внутри
репозитория также объявляется входом. Неявные Windows batch-файлы запрещены:
если нужна оболочка, оператор явно указывает её как интерпретатор.

До первого процесса проверяются все объявленные команды, наличие программ и
входов, ограничения аргументов и общий лимит входных файлов 16 МиБ. Отказ
оставляет workflow для инженерного исправления без запуска частичного набора.
Снимок сохраняет хеши и идентичность входов. Изменение контекста до следующей
команды или применения результата не превращает старый PASS в новый допуск.

`repeat: per-attempt` означает одно исполнение в существующей сохраняемой
попытке gate. После неизвестного исхода действует прежняя инженерная сверка,
а не автоматический повтор. Новый раунд может иметь новую попытку. Это не
доказательство идемпотентности произвольного скрипта и не песочница: проверка
исполняется с правами процесса PromptPilot. Установку зависимостей следует
выполнять при подготовке окружения, проверку — после результата исполнителя.

Ранее утверждённые shell-строки сохраняют прежний способ исполнения и форму
снимка для восстановления старых попыток. Автоматического преобразования
сохранённой строки в argv нет. Редакторы настроек и этапов принимают по одной
команде или JSON-объекту на строке; строка в JSON позволяет сохранить старую
многострочную команду. Ошибка JSON не превращается в shell-команду.

отдельно; сама эта доработка не закрывает всю заявку.
