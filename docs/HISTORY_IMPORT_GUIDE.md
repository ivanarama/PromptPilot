# Перенос старой истории в Workflow Orchestrator

Этот механизм нужен для плавного переезда: прежние итерации не теряются, а
новые раунды уже записываются PromptPilot автоматически. История импортируется
только в `draft` workflow, до команды `workflow start`.

## Что переносить автоматически, а что вручную

Автоматически или полуавтоматически стоит извлекать факты, которые можно
пересчитать либо однозначно найти в репозитории:

- commit SHA, ветку и состояние рабочего дерева;
- имена, размеры и SHA-256 артефактов;
- результаты pytest/build/runtime gate из логов и evidence manifest;
- timestamps, число раундов, findings и смены verdict;
- число прошедших, упавших и пропущенных тестов.

Вручную добавляются сведения, которых нет в машиночитаемых источниках:

- почему было принято инженерное решение;
- какую гипотезу проверяли;
- что сообщил клиент и как это повлияло на приоритет;
- где раунд пришлось реконструировать по переписке;
- наблюдения, выводы и материал для будущей статьи.

Ручной факт не становится проверенным только потому, что попал в импорт.
Каждый факт получает собственный источник и статус.

## Статусы фактов

| Статус | Когда использовать |
|---|---|
| `VERIFIED` | Факт подтверждён файлом, Git, логом, manifest или повторяемой проверкой |
| `CLAIMED` | Так было заявлено исполнителем, но независимо ещё не проверено |
| `PARTIAL` | Подтверждена только часть утверждения |
| `DISPROVED` | Проверка показала, что утверждение неверно |
| `INFERRED` | Факт логически восстановлен из нескольких источников |
| `UNKNOWN` | Данных недостаточно |

Для статьи безопасно автоматически использовать `VERIFIED`; остальные статусы
нужно либо перепроверить, либо явно описать как заявления/реконструкцию.

## Формат JSON

```json
{
  "idempotency_key": "ut10-pre-promptpilot-v1",
  "source": "git + docs/audit + manual reconstruction",
  "notes": "Раунды до включения Workflow Orchestrator",
  "rounds": [
    {
      "round_no": 1,
      "status": "revision_required",
      "base_sha": "592e947",
      "candidate_sha": "b13cfa7",
      "audit_sha": "8744181",
      "summary": "Аудитор вернул реализацию на доработку",
      "metrics": {
        "pytest_passed": 1048,
        "pytest_failed": 0
      },
      "facts": [
        {
          "claim": "Исполнитель сообщил о прохождении 1048 тестов",
          "status": "CLAIMED",
          "source": "UT10-BP3_U3_IMPLEMENTATION_REPORT.md",
          "evidence": ["pytest: 1048 passed"],
          "notes": "До независимого воспроизведения"
        },
        {
          "claim": "Commit аудита существует в Git",
          "status": "VERIFIED",
          "source": "git rev-parse 8744181",
          "evidence": ["8744181"]
        }
      ]
    }
  ]
}
```

`expected_version` в файле не нужен: CLI подставляет актуальную версию draft,
чтобы старый файл не мог затереть новое состояние.

Допустимые статусы исторического раунда: `completed`, `failed`, `cancelled` и
`revision_required`. Номера раундов должны быть уникальны. Повтор того же файла
с тем же `idempotency_key` безопасен; попытка заменить его содержимое другим
с тем же ключом отклоняется.

## Порядок миграции

1. Создать `workflow.json` и draft:

   ```powershell
   pp workflow create .\workflow.json
   ```

2. Подготовить и проверить исторический JSON. Не помечать пересказ исполнителя
   как `VERIFIED` без независимого источника.
3. Импортировать его:

   ```powershell
   pp workflow import-history ut10-bp3-u3 .\ut10-history.json
   ```

4. Проверить timeline:

   ```powershell
   pp workflow rounds ut10-bp3-u3
   pp workflow events ut10-bp3-u3 --json
   ```

5. Начать первый новый раунд:

   ```powershell
   pp workflow start ut10-bp3-u3 --base-sha <reviewed-commit>
   ```

## Совместное использование с W3

После импорта старых раундов можно включить planner и автономный обмен ходом
между executor, gate и reviewer. Кнопки `Экспорт JSON` и `Экспорт Markdown`
объединяют импортированные provenance-факты с новыми планами, этапами, attempts,
findings и append-only events. Полностью готовый `article-source.md`, постоянный
candidate worktree и физически read-only среда аудитора остаются дальнейшими
этапами; текущий report уже служит проверяемым источником статистики для статьи.
