# Наблюдение за очередью FIX

Команда `observe-fix` читает уже сохранённый JSON проверки состояния и показывает,
как его кандидаты соотносятся с настройками FIX. Её вызывают вручную из CLI.
Расписание и запуск задач работают по действующим настройкам экземпляра.

```bash
pp pipelinectl --config pipelinectl.json observe-fix --health-file health.json
pp pipelinectl --config pipelinectl.json observe-fix --health-file health.json --reservations-db promptpilot.db
```

`health.json` должен содержать сохранённый результат checker для этого проекта,
включая `state`, `findings` и списки кандидатов соответствующего маршрута.
Используйте свежесть и происхождение исходного снимка при сравнении отчётов.
Если JSON указывает репозиторий, команда сверяет его с конфигурацией. Ошибка
чтения, красное состояние и неполный список нужного маршрута возвращают
диагностику вместо пустой очереди.

| Маршрут | Что показывает команда |
| --- | --- |
| `legacy` | Кандидаты из сохранённого списка `fix_candidates`. Выбор и повторная проверка остаются в скиле FIX. |
| `parallel` | Список `fix_candidates` в том же порядке, который использует параллельный FIX. Доработки PR идут перед новыми issues. |
| `source_bound` | Порядок `technical_fix_candidates` и обычные кандидаты вне этого маршрута. Отдельные операции восстановления и приёмки остаются в действующем диспетчере. |

При заданном `--reservations-db` команда читает резервы из указанного SQLite
через соединение только для чтения. Она учитывает резерв, пока совпадающая
попытка локального worker ещё работает, даже если срок резерва вышел. Без
указанного файла локальная занятость обозначена как неизвестная. Отсутствие
локального резерва не даёт допуска к работе на другом компьютере.

Команда не выполняет checker, синхронизацию Git, запросы к GitHub, выбор
исполнителя или запись в базу. Её результат описывает кандидатов, а
фактическое назначение дополнительно зависит от свежих проверок, лимитов,
состояния других попыток и правил проекта.

Для проверки команды использовали сохранённый снимок профиля OneBase. В нём
checker опубликовал 93 кандидата FIX, а отчёт сохранил все 93 номера и определил
маршрут `legacy`. Число кандидатов относится к снимку, доступность отдельных
задач в момент будущей выдачи определяется заново.

## Где подключать общее резервирование

- Плановый legacy FIX выполняет выбор в репозиторном `fix-approved`. Допуск
  расписания учитывает состояние очереди, но сам по себе не выдаёт точное
  назначение на issue. Ручной запуск скила идёт по той же процедуре.
- `pipelinectl next fix` в параллельном режиме использует
  `_elect_fix_candidate` и реестр `pipeline_target_reservations`.
- Режим с технической передачей PR использует `review_routing_fix` или
  `review_routing_pipeline_fix`. Оба пути резервируют конкретную цель в том же
  реестре и дополнительно проверяют свежие доказательства на GitHub.
- MCP-задания, созданные как отдельные внешние workflow в ветке внешнего
  исполнения, привязаны к раунду и сессии клиента. Перед включением выдачи
  общей очереди нужно связать этот маршрут с тем же резервом проекта.
- Для пилота следует сначала подключить плановый FIX и ручной FIX к одному
  резервированию. Этапы ревью и слияния сохраняют собственные условия.
