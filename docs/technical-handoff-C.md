# Срез C: наблюдение технической передачи

Работа PromptPilot #153 после общей приёмки B (#228 / OneBase #2453).
Парная кодовая задача — OneBase #1910, принятый план — 195, родитель — #1836.

Граница: раздельные technical/engineering handoff, product/safety решения,
insufficient data и ошибки инструментов в Dashboard API/UI. Оператору нужны
точный PR/HEAD, категория, evidence, получатель, расход попыток/лимит и время
перехода. Продуктовая развилка показывает варианты поведения и рекомендацию.

Наблюдение не меняет допуск REVIEW/FIX/MERGE, ship, source proof и бюджет.
Старые корзины сохраняются; неизвестные и устаревшие данные не означают ноль.

Код проверяется через публичные API/UI и настоящие Go health/run fixtures,
полным native pytest, независимым ревью и пятью обязательными CI. Общая приёмка
также требует проверок парной версии OneBase и всех восьми её обязательных CI.

Новая immutable пара, staging, ограниченный пилот и установка — отдельный
операторский остаток, связанный с обоими кодовыми PR. Документ описывает
реализацию; выполненный пилот и календарные метрики им не объявляются.
Рабочие флаги и установленная версия не меняются до соответствующих гейтов.

Windows automation остаётся OFF. История неизвестного executor Task38 и его
карантин сохраняются. Двухлинейный FIX-пилот #140 имеет собственную приёмку.

## Представление данных

`GET /api/pipeline-insights/{profile_id}` возвращает дополнительный `routing`;
в отчёте `GET /api/pipeline-insights/{profile_id}/report` это `board.routing`.
Dashboard «Состояние» и «Отчёт» показывают раздельные группы technical,
engineering, product, safety_exception, insufficient_data, tool_error и unknown.
Один PR со смешанными причинами может присутствовать в нескольких группах:
их количества нельзя складывать как число PR. Legacy-корзины не переименованы.

Источник категорий — `routing_observation` версии `routing-observation-v1`
согласованного Go checker. PR/current full HEAD, immutable source/report hash,
получатель, lifetime budget и время именованного server event сохраняются.
Product показывает варианты поведения, последствия и рекомендацию с причиной.
Старые HEAD/epoch не выдают прежний блокер за текущий. Отсутствие расширения,
протухший/неполный cache и усечение не превращаются в подтверждённый ноль.

Tool_error — фактически failed execution выбранной серии за период отчёта.
Вердикт модели «НУЖЕН ЧЕЛОВЕК» или «НЕ СМОГ» сам по себе им не является.
Более поздний completed run отмечает окончание предыдущего execution incident;
пауза серии, PID и отмена такого доказательства не дают. Это отображение не
обнуляет quarantine/reservation и не разрешает повторный запуск процесса.

Оба GET по умолчанию используют локальные данные, не обновляют GitHub,
не вызывают провайдера и не принимают решение о dispatch/merge. Текст evidence
экранируется в UI. Новых action buttons или автоматического ship здесь нет.

Согласованная установка и реальная приёмка отслеживаются в OneBase #2455.

## Воспроизводимые данные для проверки

Восемь полных health JSON в `tests/fixtures/routing-observation-v1.json`
получены публичным Go CLI из исторических protocol fixtures с фактическими
четырьмя каноническими consumer trees на коммите OneBase
`66239703ab6368e21e0065a971b871e55b54eec5`. Это исходный immutable producer,
а не выдуманный SHA будущего финального коммита. Origin содержит source blobs,
tree, команду, SHA256 данных и бинаря. Файлы закреплены как LF.

Данные офлайн и синтетические: они не предоставляют execution authority.
API-тест публикует их в обычный durable cache, обращается к обоим GET и Markdown,
передаёт настоящий API-ответ реальному JS renderer. Отдельно проверяются старый
checker/cache, фактический SQLite failed run и последующий completed run.
