# Обычный BEHIND → проверенный base-sync → carry

При парной проверке #42 обнаружился пропущенный первый переход. Настоящий
checker OneBase `29a79fb1` относит проверенный PR с `ship` к обычному `merge`,
пока его HEAD ещё не обновлён. Он не создаёт integration owner заранее.
Старый тест задавал такого владельца искусственно, поэтому не замечал, что
обычный `BEHIND` всё ещё возвращал полный скил.

При **обоих** явных `base_sync_merge: true` и `base_sync_carry: true` обычный
первый MERGE-кандидат теперь получает отдельный подписанный ticket
`ordinary-base-sync-v1`. Это один MERGE lane, не механизм параллельных MERGE.
Без обоих флагов прежний обычный fallback сохраняется.

Перед выдачей и непосредственно перед обновлением заново проверяются первая
цель текущего health, отсутствие integration owner и барьера, актуальные HEAD,
base, неизменённый канонический `reviewed` proof и trusted `ship`, обязательный CI,
доверенный аккаунт, конфигурация, исключения и срок ticket. Нужен Git с
`merge-tree --write-tree`: неподдерживаемый инструмент возвращает старый fallback.

Ticket имеет отдельные purpose/mode, HMAC и срок 300 секунд. Чужой purpose,
изменённая подпись и снятая подпись не попадают в обычный MERGE. Обновление
использует [документированный `expected_head_sha`](https://docs.github.com/en/rest/pulls/pulls#update-a-pull-request-branch); результат 202 означает
только принятие запроса. Оно не считается доказательством нового HEAD.

До единственного PUT сохраняется ATTEMPTED. После входа в writer снова
проверяются live gates, после commit — ещё раз. Отказ до входа в mutator помечается
REFUSED. Ошибка запроса, потерянный ответ, 422 или неувиденный результат оставляют
попытку потраченной: автоматического повторного PUT нет. Только операторская
инженерная сверка может разрешить неизвестный исход; TTL не даёт повторного запуска.

Журнал находится рядом с **абсолютным приватным signing-key path** в
`base-sync-updates-v1/receipts.sqlite3`, отдельно от очищаемого comment cache.
`initialized.json` связывает установленный store с его UUID: потеря одного из
этих файлов не создаёт пустой новый журнал. Каталог, signing key и резервные
копии относятся к доверенному состоянию оператора; удалять или откатывать их
как временный кэш нельзя. Независимые MERGE-контроллеры с разным приватным
состоянием этим протоколом не координируются и не поддерживаются.

Readback проверяет двух родителей `[old_head, base]`, актуальную базовую ветку,
ancestry и побайтово воспроизведённое бесконфликтное дерево, затем повторно HEAD.
Только после этого возвращается `updated`; сохранённое подтверждение имеет
отдельную HMAC purpose и привязку к ticket. Потерянный ответ можно восстановить
чтением с тем же ticket, даже после его истечения или выключения флагов.
Такое восстановление не разрешает новый PUT.

Дальнейший MERGE выполняет существующий carry: он независимо проверяет все четыре
условия, свежий CI нового HEAD, proof, `ship`, epoch и CAS. Обновление ветки само
по себе не публикует review/base-sync/merge-done и не утверждает успех слияния.
Разрешение конфликтов, несколько последовательных carry и старый экспериментальный
путь обновления уже существующего integration owner этим срезом не расширяются.

## Проверка пары

`tests/test_ordinary_base_sync.py` идёт через публичные `next/complete merge`
на настоящем частном Git-графе. Для реального checker вместо health-double
оператор задаёт три переменные только в изолированном тестовом окружении:

```
PP_ACCEPTANCE_HEALTH_BIN=/absolute/path/pipelinehealth
PP_ACCEPTANCE_HEALTH_SHA256=<проверенный SHA256 бинаря>
PP_ACCEPTANCE_HEALTH_CONTRACT=/absolute/path/.claude/skills/review-queue/SKILL.md
```

Проверяются update → carry → merge → cleanup, отрицательные границы, потеря
ответа, пропажа receipt, истечение после writer admission и два конкурирующих
публичных complete. GitHub остаётся fixture transport; модели и рабочие сервисы
не запускаются. Это парная проверка реализации, **не production throughput-пилот**.
Рабочие флаги остаются OFF до отдельного ограниченного пилота на допустимой цели.
