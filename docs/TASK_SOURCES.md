# Источники единого списка задач

Один интерфейс может читать задачи нескольких **явно зарегистрированных**
экземпляров PromptPilot. Это представление для наблюдения: базы данных, очереди,
права, аренды и исполнители остаются у каждого экземпляра. Удалённые строки всегда
имеют `readonly=true`; управление ими через агрегированный список не предоставляется.

## Настройка в интерфейсе

В **Настройки → Источники** нажмите **Добавить источник**. Укажите понятное имя,
адрес экземпляра, тип **PromptPilot** и способ авторизации. Например, имя
«Студия · Windows» и адрес `https://studio-windows.example`. Адрес указывает на
экземпляр API, без суффикса `/api/task-feed`. Название сайта или проекта не является
отдельным типом источника.

**Проверить подключение** проверяет введённые параметры без сохранения. Удалённому
backend отправляются только ограниченные GET-запросы. Проверка не запускает
Workflow и не изменяет удалённую очередь. **Сохранить** регистрирует источник
в текущем backend; после этого он участвует в общем списке задач. Удаление
источника убирает подключение из этого списка, не отменяя его удалённые задачи.

Для доступа можно оставить текущую авторизацию, задать новый токен или выбрать
подключение без токена. Токен — поле только для записи: после сохранения он
хранится на backend и при повторном открытии формы не показывается. Пустое поле
при редактировании сохраняет существующую привязку на том же адресе. Для явного
отказа от авторизации выберите режим без токена. При смене адреса нужно указать
новый токен либо явно отказаться от авторизации: старый credential автоматически
на другой адрес не переносится.

Признак настроенной авторизации не подтверждает наличие или пригодность ключа.
Например, backend может потерять доступ к файлу токена или переменной окружения.
Результат отдельной проверки подключения показывает фактическую доступность.
Сохранённый ключ или его внутренний путь в эту форму не загружаются.

Если настройки изменились в другой вкладке, запись получает конфликт версии.
Обновите список и проверьте изменения перед повторным сохранением. Некорректный
реестр или неподходящие права доступа отключают редактирование с понятной ошибкой;
существующий файл при этом не заменяется пустым списком.

## Файл регистрации

Без зарегистрированных источников общий список содержит только локальные задачи.
Интерфейс и ручная регистрация используют один реестр. По умолчанию backend читает
`<PP_DATA_DIR>/task-sources.json`; путь можно заменить переменной
`PP_TASK_SOURCES_FILE`. Пример формата, который сам по себе ничего не подключает:

```json
{
  "version": 1,
  "sources": [
    {
      "id": "studio-windows",
      "label": "Студия · Windows",
      "base_url": "https://studio-windows.example",
      "token_env": "REMOTE_PP_TOKEN"
    },
    {
      "id": "remote-worker",
      "label": "Удалённый worker",
      "base_url": "https://remote-worker.example",
      "token_file": "private/remote-worker-token.txt"
    }
  ]
}
```

Подключение добавляет владелец backend явным действием в настройках или файле.
Удалённый ответ, prompt или задача не могут зарегистрировать новый адрес.
`id` содержит строчные латинские буквы, цифры, `_` и `-`, начинается с буквы и
имеет длину до 48 символов. `local` зарезервирован. Можно зарегистрировать до
16 источников. Модуль чтения ограничивает сырой файл 64 записями и 256 КиБ:
повторяющиеся ID пропускаются целиком, ошибка одной записи не отключает остальные
корректные источники в ленте. Редактирование через настройки требует полностью
валидного реестра не более чем из 16 источников; повреждённый реестр автоматически
не переписывается.

`token_env` и `token_file` взаимоисключающие. Первая настройка называет переменную
окружения **backend**, вторая — файл с одним UTF-8 токеном длиной не более 8192 байт.
Относительный путь считается от каталога файла регистрации. Перевод строки в конце
файла допускается. Нужен отдельный файл токена, а не общее JSON-хранилище
учётных данных приложения. Значения токенов, имена их переменных, пути файлов,
URL и конфигурации источников не входят в read model общего списка и удалённой
карточки. API настроек отдельно возвращает редактируемые имя и адрес, но не ключ
и не внутренний путь к нему. При отсутствии настроенного credential источник недоступен;
текст исключения, ответ сервера и stack trace пользователю не передаются.

Backend использует только GET, с абсолютным пределом ожидания 2 секунды на HTTP-операцию, пределом
ответа 2 МиБ и максимумом 10 запросов на источник за одно чтение. До четырёх
источников читаются параллельно. Настройки proxy/auth из окружения не наследуются,
redirect запрещён, URL с userinfo, query или fragment не принимаются. HTTP разрешён
только для loopback; другой компьютер подключается через заранее подготовленный
HTTPS endpoint или loopback-туннель. Автоматического обнаружения компьютеров нет.
Loopback текущего backend на его собственном порту не может быть источником.

Медленная передача байтов не продлевает ожидание API. Поток чтения проверяет
монотонный срок между порциями данных. Зависший системный DNS или разбор HTTP
заголовков может завершиться в фоне уже после отказа caller; одновременно
существует не более 16 таких GET. Новые чтения при занятой ёмкости получают
`unavailable`, без создания неограниченного числа потоков. Поздний ответ отменённого
чтения не публикуется. Это ограничение ожидания и ресурсов, а не обещание
мгновенной остановки системного сетевого вызова.

## Совместимость и границы

Новый peer читается через `GET /api/task-feed?local_only=true&limit=100&offset=…`.
`local_only=true` исключает рекурсивную агрегацию. В ответ дополнительно принимаются
только строки с `source_id=local`; ID заново строится как
`<source_id>:<kind>:<object_id>`. Совпадение числовых ID на разных компьютерах
не объединяет задачи.

**Только HTTP 404** включает совместимость со старым peer:
`GET /api/workflows?limit=100&offset=…`. Такие строки имеют статус источника
`partial` и пояснение: **старый API источника, доступны только Workflow; для
полного списка задач обновите PromptPilot на источнике**. Это ограничение версии
контракта, а не признак отсутствия бизнес-задач. Сырые LLM-задачи
старого peer не загружаются: не делаются предположения по заголовкам или промптам,
какая из них является бизнес-задачей. Ошибки доступа, timeout, redirect или неверный
JSON дают `unavailable`, а не сообщение об отсутствии задач.
Короткая страница нового peer дочитывается до заявленного total в пределах
10 GET; при усечении или повторяющихся ID статус остаётся `partial`. Total,
противоречащий полученным строкам, считается ошибкой источника.

Карточка нового peer читается через
`GET /api/task-feed/local/{kind}/{object_id}`. Для workflow и только при 404
используются старые GET workflow, rounds, runs и events. Загружаются первые пять
раундов, до 100 запусков каждого и до 200 событий; усечение отмечается в истории.
История группируется по ролям, в том числе «Проверяющий». Ни sync, ни advance,
ни start/dispatch/cancel, ни другой изменяющий запрос не вызывается.

Удалённые проекции строятся по белому списку. `config`, `workorder_guard.lease_token`,
input/output JSON, payload событий и текст отчёта в общий список и удалённую карточку
не передаются. Для результата доступны только наличие, размер текста, хеш,
отметка завершения и вердикт. Агрегатор не является браузером произвольных API.

Приложение, которое создаёт Workflow после явного подтверждения запуска, может
показывать эти процессы через собственный экземпляр PromptPilot. Для стадий заявки
до создания Workflow нужен отдельный авторизованный read model приложения.
[Отдельный пример интеграции сайта](examples/website-workflow-source.md) описывает
эту границу без привязки основного контракта к конкретному проекту.

Регистрация источника не создаёт доступ, туннель или интеграцию приложения.
Владелец каждого backend отдельно настраивает сетевой доступ и credential.

## HTTP API настроек

Эти маршруты используют ту же авторизацию и ограничения Host/Origin, что и
остальной API текущего backend. Они управляют регистрацией источников; удалённый
трафик по-прежнему ограничен GET. Credential не становится полем публичного списка
задач и никогда не возвращается как сохранённое значение токена.

| Маршрут | Назначение |
| --- | --- |
| `GET /api/task-sources` | Читать `revision`, `editable`, `sources` и `errors`. |
| `PUT /api/task-sources/{id}` | Создать или изменить один источник с текущей `revision`. |
| `DELETE /api/task-sources/{id}` | Удалить регистрацию с текущей `revision`. |
| `POST /api/task-sources/probe` | Проверить сохранённый источник или несохранённый черновик, не меняя реестр. |

Элемент настроек содержит `id`, `label`, `type="promptpilot"`, `base_url`,
`has_token` и `auth_kind` (`none`, `env`, `file` или `managed`). `has_token`
означает наличие привязки к credential, а не успешную проверку ключа. В ответе
нет самого токена, имени переменной окружения или пути к файлу.

Для PUT передаются `id`, `label`, `base_url`, `revision`, необязательный
`type="promptpilot"`, write-only `token` и `auth_mode`:

- `preserve` сохраняет прежнюю привязку, если новый токен не передан;
- `none` явно убирает авторизацию у этой регистрации;
- `token` задаёт новый токен или использует уже настроенный на том же адресе.

ID в теле должен совпадать с ID маршрута. Он остаётся стабильным при изменении
отображаемого имени. `revision` берётся из последнего GET настроек; устаревшая
версия даёт HTTP 409. DELETE принимает объект `{"revision": "…"}`. При
неподтверждённом сохранении или удалении сначала перечитайте настройки; не
считайте исключение доказательством отката.

Probe принимает **либо** `{"source_id": "studio-windows"}`, **либо**
`{"draft": {...}}`. Черновик содержит те же поля источника, что PUT, но без
`revision`. Переданный для проверки токен используется только в памяти и не
сохраняется. Ответ содержит `status`, `message`, `api` и `capabilities`:

| Результат | `api` | `capabilities` |
| --- | --- | --- |
| Новый API задач доступен | `task-feed` | `tasks=true`, `workflows=true` |
| После 404 доступен только старый API Workflow | `workflows` | `tasks=false`, `workflows=true` |
| Нет доступа, timeout или неверный ответ | `null` | `tasks=false`, `workflows=false` |

Новые токены, введённые через UI/API, записываются в закрытые управляемые файлы
backend. При смене или удалении подключения старые и неопределённые credential
файлы сохраняются для безопасной сверки; внешний файл ключа не удаляется.
Изменение реестра не расширяет права самого удалённого API-токена и не заменяет
проверки удалённого экземпляра.

## Python-контракт

```python
list_source_items(*, sources_file=None)
# {items: [...], sources: [{id, label, status, readonly, ...}], errors: [...]}

get_source_detail(source_id, kind, object_id, *, sources_file=None)
# {item, history, result, artifacts, source} либо {item: None, source, error}
```

Поддерживаются только `kind=workflow` и `kind=task`. Для task нужен положительный
целочисленный `object_id`. Ошибки регистрации и источников — данные представления;
они не прерывают выдачу локальных задач и других исправных источников.
