# Маршруты заявок (flows)

Заявки извне — предложение игрока с формы сайта, письмо клиента, задача от
команды — раньше принимал отдельный скрипт на каждый случай. Маршрут делает
то же одним движком: сценарий описывается файлом, а не программой.

## Коротко

- **Маршрут** — JSON-файл в `~/.promptpilot/flows/` (или в `PP_FLOWS_DIR`):
  откуда приходят заявки, насколько им доверять и какие шаги они проходят.
- **Заявка** идёт по шагам: агент, человек, команда, публикация, финиш.
  Условия (`when`) пропускают шаги, повторы (`repeat`) возвращают назад.
- **`pp flows run`** читает входы и двигает заявки. `start.ps1` и трей
  запускают его сами, если в каталоге есть маршруты. Агентские шаги — обычные
  задачи очереди: их выполняет обычный worker, с [правами задачи](../README.md#права-задачи).
- **Решает человек** там, где маршрут это говорит: кнопки в Telegram, окно
  «📨 Заявки» в веб-интерфейсе, `pp flows approve/reject`.
- **Журнал** каждой заявки — только дописывается: кто, когда, что решил,
  что вернул агент, чем кончилась команда.

## Доверие

У маршрута есть поле `trust` — чей текст он принимает. От него зависит, что
маршруту можно, и **маршрут, нарушающий эти пределы, не загрузится вовсе**:

| `trust` | Чей текст | Права агента до согласования человеком | после | Что можно подставлять в команды и пути |
|---|---|---|---|---|
| `owner` | ваш собственный | любые | любые | что угодно |
| `team` | коллег | любые (задаются явно) | любые | только «надёжные» значения |
| `client` | клиентов | `none` / `read` | до `write` | только «надёжные» значения |
| `public` | кого угодно | `none` / `read` | до `write` | только «надёжные» значения |

- **Согласование** — шаг `human` без условия `when` и с `on_reject: reject`:
  отказ человека завершает заявку. Шаг, который можно пропустить, ничего не
  открывает.
- **«Надёжные» значения** — те, что не может написать автор заявки: номер
  заявки (`item.id`), константы маршрута (`flow.*`), поля ответа агента со
  схемой `enum` или `integer`, код возврата команды, решение человека.
  Текст заявки, её тема, ник, текстовые поля ответов агентов и вывод команд в
  командную строку и пути не попадают никогда.
- **Текст извне в промпте** обрамляется блоком `<<<ВНЕШНИЙ ТЕКСТ … ВНЕШНИЙ ТЕКСТ>>>`
  с пояснением, что это данные, а не указания; закрыть рамку изнутри текста
  нельзя. Материалы владельца (`material`) и пометки человека не обрамляются.
- **Публичная страница** получает только перечисленные поля, одной строкой,
  без ссылок, в пределах длины.

## Файл маршрута

```json
{
  "name": "kt-proposals",
  "title": "Предложения игроков",
  "trust": "public",
  "vars": {"game": "C:/Projects/kt-game", "site_feed": "C:/Projects/site/kt/feed.json"},
  "input": {"type": "email", "host": "imap.mail.ru", "user_env": "KT_IMAP_USER", "password_env": "KT_IMAP_PASSWORD"},
  "limits": {"per_day": 20, "per_author": 3},
  "notify_chat_ids": [],
  "steps": [ … ]
}
```

| Поле | Что это |
|---|---|
| `name` | имя маршрута: `a-z`, цифры, `-`, до 40 символов |
| `title`, `description` | для людей |
| `trust` | `owner` / `team` / `client` / `public`, см. выше |
| `vars` | константы маршрута: пути, адреса — в шаблонах как `{{flow.<имя>}}`; `{{flow.dir}}` — папка файла маршрута |
| `input` | откуда брать заявки (сейчас — почтовый ящик); без него заявки заводят вручную |
| `limits` | `per_day` — заявок в день на маршрут, `per_author` — на одного автора |
| `notify_chat_ids` | кому в Telegram слать согласования; пусто — всем авторизованным в боте |
| `steps` | шаги по порядку, до 40 |

### Шаги

У каждого шага есть `id` (`a-z`, цифры, `_`), необязательные `title`, `when` и `repeat`.

**`agent`** — задача агенту:

| Поле | Что это |
|---|---|
| `provider`, `model`, `effort` | как у обычной задачи |
| `rights` | права: `none` / `read` / `write` / `full` (вне `owner` — обязательно) |
| `working_dir` | папка задачи (шаблон; создаётся, если её нет) |
| `prompt` или `prompt_file` | текст задачи; файл — относительно папки маршрута |
| `material` | материалы владельца в промпт: `{"концепция": {"file": "{{flow.concept}}", "max": 8000}, "структура": {"tree": "{{flow.game}}", "depth": 2}}` — в шаблоне `{{material.концепция}}` |
| `output` | схема ответа: `{"verdict": {"enum": ["ДА", "НЕТ"]}, "priority": {"type": "integer", "min": 1, "max": 10}, "reason": {"type": "text", "max": 300}}` |
| `retries` | сколько раз перезапустить при сбое или ответе не по схеме (0–3) |
| `timeout`, `priority` | как у обычной задачи |

С `output` агент заканчивает ответ блоком — PromptPilot сам дописывает это требование в промпт:

```
PP_RESULT_JSON_BEGIN
{"verdict": "ДА", "priority": 3, "reason": "…"}
PP_RESULT_JSON_END
```

Берётся последний блок; `enum` сверяется без учёта регистра и хранится в
каноническом написании, число — в пределах, текст обрезается до `max`.
Значение вне схемы — не догадка, а ошибка: шаг повторится (`retries`) или
заявка остановится для человека.

**`human`** — решение человека: `text` (шаблон), `show` — что показать
(`["steps.triage.reason", "steps.triage.spec"]`), `notify` (по умолчанию да),
`on_reject`: `reject` (отказ завершает заявку) или `continue` (идти дальше;
решение лежит в `steps.<id>.decision`, пометка — в `steps.<id>.note`).

**`command`** — команда без оболочки: `run` — список аргументов (шаблоны),
`cwd`, `timeout` (с), `ok_codes` (по умолчанию `[0]`), `require_output` —
регулярное выражение, которое должно найтись в выводе, `on_error`: `human`
(по умолчанию) / `fail` / `continue`, `output_json` — разобрать stdout как
JSON-объект в поля шага, `output_limit`. Результат: `exit_code`, `ok`,
`output`. Команде доступны `PP_FLOW` и `PP_FLOW_ITEM`.

**`publish`** — публичная лента (`to: json_feed`): `path` (только `{{flow.*}}`),
`fields` — поля записи (шаблоны), `caps` — длины полей (по умолчанию 300),
`stages` — подписи этапов, `hide` — какие завершённые заявки не показывать
(по умолчанию `["cancelled"]`), `limit` — записей в ленте.

**`finish`** — конец: `status` `done` / `rejected` / `failed`, `note`, `notify`.

### Условия и повторы

```json
{"id": "declined", "kind": "finish", "status": "rejected",
 "when": {"step": "triage", "field": "verdict", "in": ["ОТКЛОНИТЬ"]}}
```

`when` — шаг выполняется, только если поле результата более раннего шага
входит (`in`) или не входит (`not_in`) в список. Поля проверяются при
загрузке: опечатка в значении `enum` — ошибка файла, а не условие, которое
никогда не сработает.

```json
"repeat": {"from": "implement", "when": {"step": "check", "field": "ok", "in": [false]}, "max": 2}
```

`repeat` — после шага, пока условие держится, вернуться к более раннему шагу,
не больше `max` раз. Потом — человеку (`on_exhausted: human`, по умолчанию)
или дальше (`continue`).

### Подстановки

| Шаблон | Что это |
|---|---|
| `{{input.body}}`, `{{input.subject}}`, `{{input.from}}` … | поля заявки (у письма: `from`, `reply_to`, `subject`, `title`, `author`, `body`, `date`) |
| `{{item.id}}`, `{{item.title}}`, `{{item.author}}`, `{{item.created_at}}` | заявка |
| `{{steps.<id>.<поле>}}` | результат шага |
| `{{flow.<имя>}}`, `{{flow.dir}}`, `{{flow.name}}` | константы маршрута |
| `{{material.<имя>}}` | материал владельца (только в промпте агента) |
| `{{что-то\|запасной текст}}` | запасной текст, если значения нет |

## Когда нужен человек

Заявка останавливается со статусом «нужен человек», если агент сбоит или
отвечает не по схеме сверх `retries`, команда вернула ошибку, повторы
исчерпаны, шаг, на котором заявка стояла, из маршрута убрали. В Telegram
приходит сообщение с кнопками, в «📨 Заявках» — те же действия:

- **Повторить** — выполнить шаг ещё раз; после исчерпанных повторов — ещё один круг;
- **Пропустить** — идти дальше, как будто шаг прошёл (согласование не пропускается — по нему решают);
- **Снять** — завершить заявку и остановить задачу её шага.

Маршрут можно править на ходу: заявки держатся за `id` своего шага, а не за
номер. Пока файл маршрута не проходит проверку, его заявки просто ждут.

## Вход: почтовый ящик

```json
"input": {
  "type": "email",
  "host": "imap.mail.ru", "port": 993,
  "user_env": "KT_IMAP_USER", "password_env": "KT_IMAP_PASSWORD",
  "folders": ["INBOX"],
  "subject_marker": "KT",
  "require_from_domain": "formsubmit.co",
  "dkim_authserv": "mxs.mail.ru",
  "allow_from": [],
  "author_pattern": "(?mi)^\\s*name\\s*:\\s*(.+)$",
  "generic_subjects": ["Предложение по игре"],
  "body_limit": 5000,
  "every": 120
}
```

- Логин и пароль — только из переменных окружения, в файле маршрута их нет.
- Ящик читается, ничего не помечая прочитанным. Письмо сначала судят по
  заголовкам и только годное читают целиком: маркер темы (`[KT]`, в том
  числе кириллицей), не спам, не автоответ и не рассылка, отправитель — с
  `require_from_domain` (для формы сайта — сервис формы) и, если задан
  `dkim_authserv`, с подписью DKIM этого домена в заголовке
  `Authentication-Results` **вашего** почтового сервера (чужой такой
  заголовок не считается); `allow_from` — список адресов и доменов.
- `author_pattern` достаёт автора из текста (у формы — ник), `generic_subjects` —
  общие темы формы: тогда заголовком заявки становится первая содержательная строка.
- Письмо, отвергнутое однажды, больше не разбирается. Письмо сверх `limits`
  не теряется: оно ждёт в ящике и берётся в другой день.

## Публикация: стена на сайте

Шаг `publish` пересобирает ленту из всех заявок, прошедших его, и пишет файл,
только когда записи изменились (лента может лежать в git-репозитории сайта).
Этап записи — подпись последнего пройденного шага из `stages`:

```json
"stages": {"wall": "принято", "implement": "в работе", "review": "на проверке", "done": "готово"}
```

Этапы, которые пишут в файл другие инструменты (`в релизе vX` от скрипта
релиза), сохраняются.

## Пример: «Сказки Королевства»

[`examples/flows/kt-proposals.json`](examples/flows/kt-proposals.json) — полный
пилот: предложения с формы сайта (письма от FormSubmit с DKIM) →

1. триаж хранителем концепции — агент **без инструментов**, концепция и
   структура проекта даны материалом, ответ по схеме (вердикт, причина для
   игрока, категория, приоритет, ТЗ);
2. `ОТКЛОНИТЬ` — конец; `ПРИНЯТЬ`/`УТОЧНИТЬ` — на стену сайта;
3. `УТОЧНИТЬ` — конец («нужны уточнения»); `ПРИНЯТЬ` — решение владельца;
4. ветка `kt/<номер>` в отдельной папке (`git worktree`);
5. реализация — агент с правами `write` (правит файлы, команд не запускает);
6. импорт и тесты Godot — командами; не прошли — обратно к реализации (до 2 раз);
7. ревью — агент с правами `read` видит ТЗ, вывод тестов и diff; «ДОРАБОТАТЬ» — обратно;
8. решение владельца о слиянии; отказ с пометкой — ещё круг реализации;
9. коммит и слияние в `main`; в релиз заявка попадёт через `release_kt.py --closes <номер>`.

Чтобы включить: скопировать `kt-proposals.json` и три `kt-*.md` в
`~/.promptpilot/flows/`, поправить `vars` и `input`, задать `KT_IMAP_USER` и
`KT_IMAP_PASSWORD`, проверить `pp flows check ~/.promptpilot/flows/kt-proposals.json`.
Старый скрипт `scripts/inbox/inbox_poller.py` при этом [KT]-письма брать не
должен: оставьте в его `.env` пустым `KT_CONCEPT` — клиентские письма он
продолжит принимать как раньше.

## Команды и API

```
pp flows list                  маршруты, их заявки и файлы, не прошедшие проверку
pp flows check FILE            проверить файл маршрута, ничего не запуская
pp flows items [--flow] [-s]   заявки, новые сверху
pp flows show ID [--json]      заявка целиком: вход, результаты шагов, журнал
pp flows add FLOW TITLE -t …   завести заявку вручную
pp flows approve|reject ID [--note …]
pp flows retry|skip|cancel ID
pp flows run [--once] [--interval N]
```

```
GET  /api/flows                        маршруты, счётчики, ошибки загрузки
GET  /api/flows/items                  заявки (?flow=&status=&limit=&offset=)
GET  /api/flows/items/{id}             заявка + журнал
POST /api/flows/items/{id}/decision    {"decision": "approve|reject", "note": "…", "step": "<id шага>"}
POST /api/flows/items/{id}/retry|skip|cancel
POST /api/flows/{name}/items           {"title": "…", "text": "…", "fields": {…}}
```

`PP_FLOWS_DIR` — каталог маршрутов, `PP_FLOWS_INTERVAL` — секунд между проходами (15).

## Ограничения

- Команды выполняются по очереди внутри `pp flows run`: долгая команда
  задерживает остальные заявки. Долгую работу поручайте агенту.
- Вход пока один — почтовый ящик (IMAP); публикация — JSON-лента.
- Несколько запущенных `pp flows run` безопасны — каждый переход заявки
  проверяет её версию, шаг не запустится дважды, — но смысла в этом нет.
