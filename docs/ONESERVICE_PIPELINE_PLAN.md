# Oneservice: командный конвейер разработки (GitLab → конвейер → GitLab)

Статус: план утверждён 2026-09-27. Конвейер для `C:\Projects\oneservice-cc_v2`
(GitLab: gitlab.icecorp.ru/1c/oneservice-cc_v2), разрабатывают несколько человек,
тестировщики присылают задачи.

## Принцип

Задача живёт в **GitLab issue** родного проекта команды: это бэклог, источник
прозрачности и место спора об исполнителе. PromptPilot и агенты (Claude/Codex/
ZCode) работают через GitLab API. Дашборд-«Айсберг» читает те же issues.

## Стадии (labels issue) и переходы

| Стадия (label) | Кто переводит | Что происходит |
|---|---|---|
| `подано` | бот/интейк | письмо/ТГ от человека из белого списка → issue (автор, текст, вложения) |
| `целесообразность` | хранитель (LLM) | дубликат? про этот сервис? платформенное сразу? → принято/отказ с причиной/эскалация |
| `триаж-ТЗ` | хранитель | переписать в ТЗ: файлы конфигурации, критерий готовности |
| `в работе` | человек-кнопка или PP | **claim: assignee** — кто назначился, тот держит; ветка задачи |
| `ревью` | gate по завершении | независимая модель сверяет diff с ТЗ; замечания → назад `в работе` (лимит раундов) |
| `готово-к-мержу` | ревью PASS | gate: onebase check |
| `закрыта` | мерж | merge в main,_issue закрывается, запись в документацию |

## Эскалация на платформу

Платформа = репозиторий `ivanarama/onebase` (GitHub, issues включены).
Если фикс/ревью вскрывает платформенную проблему (ошибка/ограничение onebase):
1. исполнитель завершает с вердиктом `ПЛАТФОРМА: <что именно>`;
2. конвейер создаёт issue в `ivanarama/onebase` (через gh) с ссылкой на задачу;
3. исходная задача получает label `блокирована платформой #N` и стадию
   `ждёт платформу` — видно на дашборде, почему задача спит.

## Анти-дубль исполнителей

- **claim = назначение assignee** в GitLab — атомарная операция; второй агент
  видит «занято: @кто-то» и проходит мимо;
- PP-воркер берёт только issues с label `авто` и пустым assignee;
- ручной запуск (ты сам ведёшь Claude/ZCode в папке) = назначил себя —
  конвейер обходит;
- дополнительно брони PP (`pipeline_target_reservations`) исключают два
  параллельных прогона по одной ветке.

## Вход задач (два канала, один бэклог)

Маршрутизация общего ящика tasks@mail.ru по префиксу темы:

| Тема | Куда |
|---|---|
| `[OS] …` | issues oneservice (этот конвейер) |
| `[KT] …` | игровой конвейер «Сказки Королевства» |
| остальное | общий бэклог: каталог проектов определяет проект |

- **Почта `[OS]`**: белый список отправителей (тестировщики/разрабы) → issue.
  Реализовано как `OS_ALLOW_FROM`: письмо не из списка тоже становится issue,
  но с меткой `непроверенный отправитель` — хранитель (LLM) его не читает,
  пока человек не снимет метку. Telegram-чат автора запоминается при приёме
  (`.os_authors.json`), а не ищется в тексте issue.
- **Telegram**: бот команды, доступ по паролю/telegram id из белого списка → issue.
- Автор сохраняется в issue (кто предложил — для документации); на публичных
  поверхностях показывается только ник.

## Дашборд «Айсберг»

Одна страница, метафора: над водой — то, что уже у игроков; глубина — кухня.

```
~~~~~~ ватерлиния ~~~~~~
 выше воды:   🏔 ЗАКРЫТЫ (в релизе)
 по ватерлинию: 🔍 НА РЕВЬЮ · ⏭ ГОТОВО-К-МЕРЖУ
 под водой:   🔨 В РАБОТЕ (с именем исполнителя)
 глубже:      🧊 ТРИАЖ-ТЗ · ⚖ ЦЕЛЕСООБРАЗНОСТЬ (бэклог)
 дно:         ⚓ БЛОКИРОВАНО ПЛАТФОРМОЙ · 🚫 ОТКЛОНЕНО
```

- данные: GitLab issues по labels (обновление по таймеру);
- карточка разворачивается: автор, исполнитель, ТЗ, история, ссылка на MR;
- платформенные issues — отдельный слой у дна со ссылкой на onebase.

## Документация (кто что предложил и поменял)

- каждый issue = источник: автор предложения, исполнитель, ревьюер;
- при мерже конвейер дописывает запись в `docs/CHANGELOG-TEAM.md` репозитория:
  дата · предложение (автор-тестировщик) · изменение (кто исполнил) · ревьюер · MR;
- дашборд-айсберг строит секцию «Кто что сделал» из тех же данных.

## Что нужно от людей (блокеры старта)

1. **GitLab personal access token** (api, на проект oneservice-cc_v2) —
   создаётся в GitLab → Settings → Access Tokens.
2. **Белый список**: email + telegram id каждого тестировщика/разраба.
3. **Токен ТГ-бота команды** (@BotFather, новый бот).
4. Подтверждение: платформенные issue заводим в `ivanarama/onebase` на GitHub.

## Этапы

- **Этап 0**: доступы (токены выше) + снять один несохранённый файл в репо.
- **Этап 1**: интейк почта+ТГ → GitLab issue (label `подано`), белый список.
- **Этап 2**: хранитель (целесообразность+ТЗ) + перевод стадий по verdict.
- **Этап 3**: исполнение — claim/assignee, ветка, W3-воркфлоу фикс→gate→ревью;
  эскалация `ПЛАТФОРМА`.
- **Этап 4**: мерж-скрипт (gate onebase check → merge → запись в
  документацию).
- **Этап 5**: дашборд-«Айсберг» на данных GitLab.
