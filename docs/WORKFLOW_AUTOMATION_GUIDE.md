# Автономный workflow: настройка и эксплуатация

Статус: W3 stage planner, workflow config schema version 1, report schema version 2.

PromptPilot поддерживает два режима. Старые workflow остаются ручными. Для нового
механизма оператор явно включает `automation.enabled` в UI или API; после этого
оркестратор самостоятельно передаёт управление по цепочке:

```text
executor → deterministic gate → independent reviewer
    ↑                                  │
    └──── REVISION_REQUIRED ───────────┘
                         PASS → completed
```

Для сложной новой задачи перед этим циклом можно включить планировщик:

```text
planner → утверждение плана человеком
              │
              └→ stage 1 → gate → reviewer
                    PASS → stage 2 → … → integration stage → completed
```

Планировщик не пишет код. Он исследует репозиторий и возвращает машинный план с
узкими этапами, зависимостями, разрешёнными путями, deliverables, gate-командами
и лимитом возвратов. Поэтому слабый исполнитель получает не всю большую задачу,
а один проверяемый scope за раз.

## Мастер нового workflow

Нажмите `Workflows` → `Новый workflow`. Создание оформлено как четыре явных
шага:

1. **Задача** — slug, проверяемая цель, Git-репозиторий и ветка кандидата.
2. **Команда** — отдельные provider/model/effort/timeout для planner, executor
   и reviewer; для исполнителя отдельно включаются worktree и skip permissions.
3. **Правила** — автономные переходы, лимиты, планирование и deterministic
   gate-команды.
4. **Проверка** — сводка и read-only preflight окружения.

Preflight проверяет существование Git-репозитория, допустимость имени ветки,
доступность выбранных providers и синтаксис PowerShell/sh gate-команд. Команды
проекта при этом не выполняются. Ошибка блокирует создание; предупреждение о
пустом gate разрешает продолжить, но явно фиксирует отсутствие функционального
доказательства.

В мастере есть три встроенных профиля:

- `Рекомендуемый`: сильный planner, дешёвый executor, усиленный reviewer;
- `Экономный`: более короткие лимиты и reviewer high;
- `Максимальное качество`: reviewer max и увеличенный бюджет возвратов.

Настройки можно сохранить как свой шаблон. Пользовательские шаблоны хранятся в
`localStorage` текущего браузера: это удобно для повторяющихся АА-БП3,
УТ10-БП3 и УТ11-БП3 workflow, но они не синхронизируются между компьютерами.
Цель, slug и ветка намеренно не копируются из шаблона; путь репозитория,
команда, лимиты и gates копируются.

Если включено планирование, финальная кнопка `Создать и сформировать план`
сразу создаёт черновик и запускает planner. Без planner кнопка либо запускает
одноэтапный автономный workflow, либо только сохраняет черновик — в зависимости
от переключателя автоматизации.

`skip permissions` нельзя подтвердить без отдельного worktree. Перед созданием
мастер дополнительно требует явное подтверждение опасного режима.

## Настройка существующего workflow

Откройте `Workflows`, выберите процесс и раскройте блок
`Настройки автономного workflow`. Доступны:

- код, название и проверяемая цель текущего бизнес-этапа;
- включение planner, обязательность ручного утверждения, максимум этапов и
  возвратов на этап;
- отдельные provider/model/effort/timeout и prompt template для планировщика;
- лимит новых раундов;
- отдельные provider/model/effort/timeout и prompt template для исполнителя и
  аудитора;
- отдельный worktree и `skip_permissions` для исполнителя;
- команды deterministic gate, выполняемые по одной строке;
- независимые переключатели автоматического запуска ролей, gate, применения
  вердикта и создания следующего раунда.

Сохранение настроек активного, но не терминального workflow разрешено. Изменение
цели, репозитория и ветки после старта запрещено, чтобы не менять scope незаметно
для уже созданной истории.

## Редактирование плана новой задачи

1. В мастере оставьте включённым `Сначала сформировать план этапов` и выберите
   сильную модель в роли Planner.
2. Нажмите `Создать и сформировать план`. Для повторной генерации в карточке
   доступно дополнительное поле prompt: оно дополняет, но не заменяет системные
   требования к плану.
3. После завершения planner проверьте карточки этапов. Их можно переставлять,
   добавлять и удалять; обязательны `code`, `title` и проверяемая `objective`.
4. Для каждого этапа задайте scope (`allowed_paths`), результаты
   (`deliverables`) и deterministic команды (`acceptance_gates`). Зависимость
   может ссылаться только на более ранний этап.
5. Нажмите `Сохранить и утвердить`. PromptPilot создаст первый round и при
   включённой автоматике сам запустит executor.

Даже при отключённом `require_approval` план с LLM-сгенерированными shell/gate
командами принудительно ожидает человека. Автоматически можно принять только
план без таких команд.

PASS аудитора завершает только текущий этап. Следующий этап и новый round
создаются автоматически. Workflow становится `completed` лишь после PASS
последнего этапа. Если число `REVISION_REQUIRED` достигает лимита этапа,
оркестратор переходит в `awaiting_human`; оператор может осознанно продолжить
или остановить процесс.

Для `herdr-session` необходимо задать устойчивый `herdr_target`. Для полностью
автономной работы предпочтительнее headless-provider (`agy`, `codex`, `claude` и
т. п.), которому не нужна уже открытая пользовательская панель.

## Этап вне PromptPilot (external)

Этап может выполнить человек, специалист или внешний AI-инструмент — а
проверка, доработки и история останутся в PromptPilot. В карточке этапа
выберите «вне PromptPilot» (в плане — `"execution_mode": "external"`; по
умолчанию `automatic`).

1. Когда очередь доходит до такого этапа, PromptPilot не ставит задачу агенту,
   а выдаёт **задание**: общая цель, цель и результаты этапа, ограничения,
   критерии приёмки, отчёты уже принятых этапов, замечания аудита к прошлой
   попытке этого этапа. Задание видно в карточке («Скопировать задание»),
   `GET /api/workflows/{id}/external` и `pp workflow external <id>`.
2. Workflow переходит в `awaiting_external` — «Ожидает внешнего результата».
   Это плановое ожидание, а не остановка `awaiting_human`: ничего не сломалось,
   процесс не занят, состояние переживает перезапуск.
3. Результат сдают текстом, с комментарием и сведениями об исполнителе —
   в карточке, `POST /api/workflows/{id}/external-result`
   (`{"expected_version", "run_id", "input_sha256", "result", "comment", "performer"}`) или
   `pp workflow submit <id> --assignment assignment.json -f result.md --performer "…"`.
4. Сдача не завершает этап: результат проходит gate и то же независимое ревью,
   что и работа агента (аудитор видит, что этап сдан извне и кем).
5. `REVISION_REQUIRED` возвращает этап вовне: новое задание уже содержит
   замечания аудита, результат снова ждут извне.
6. После PASS workflow идёт к следующему этапу — автоматическому или снова
   внешнему. Все версии результата и решения аудитора остаются в истории и в
   экспорте (`external_attempts`, `run.input.assignment`, `run.output.external`).

В ручном режиме (без `auto_dispatch_executor`) задание выдаётся само — оно не
запускает агента; иначе — кнопка «Выдать задание внешнему исполнителю»
(`POST /api/workflows/{id}/external-request`). Ревью всегда остаётся
независимым: выполнить вовне можно только работу исполнителя.


Для сдачи результата API требует токен именно того задания, которое видел исполнитель: `expected_version`, `run_id` и `input_sha256` из ответа `GET /api/workflows/{id}/external`. Не подставляйте текущую версию в старый результат: при новой попытке нужно заново получить задание. Веб-форма хранит черновик отдельно для каждого задания.

Для CLI сохраните задание до начала работы:

```sh
pp workflow external <id> --json > assignment.json
pp workflow submit <id> --assignment assignment.json -f result.md --performer "Имя"
```

После возврата на доработку сохраните новое задание; прежний файл не даёт права сдать старый ответ в новую попытку. Приёмка внешнего этапа относится к сданному тексту и его evidence. Она сохраняет gate и независимое ревью, но не приписывает этому этапу файлы в рабочем каталоге и не создаёт для них Git checkpoint автоматически.

## Контракт аудитора

Встроенный prompt требует две строки:

```text
AUDIT_FINDINGS_JSON: []
AUDIT_VERDICT: PASS
```

Допустимые вердикты: `PASS`, `REVISION_REQUIRED`, `HUMAN_REQUIRED`. Findings —
JSON-массив объектов с `fingerprint`, `severity`, `category`, `title`, `status`
и `payload`. Если при `REVISION_REQUIRED` массив пуст, PromptPilot сохраняет
одно агрегированное замечание уровня `medium`, а полный отчёт остаётся в run.

Невалидный контракт не угадывается по свободному тексту: workflow переходит к
человеку с событием `automation.paused`.

Формат ответа хранится в одной константе (`AUDIT_RESPONSE_CONTRACT`) и попадает в
итоговый промпт аудитора ровно один раз при любом источнике текста: встроенный
шаблон, собственный `prompt_template` роли или собственный `reviewer_prompt`
этапа. Место можно задать подстановкой `{{audit_contract}}`; без неё формат
добавляется в конец служебного блока.

## Задания этапов

`executor_prompt` и `reviewer_prompt` этапа, как и собственный `prompt_template`
роли, содержат только указания этапа. Они не заменяют контекст роли: если в
тексте нет подстановки обязательного раздела, PromptPilot добавляет раздел сам в
блок `<контекст-этапа>` сразу после текста.

| Роль | Обязательные разделы (подстановки) |
| --- | --- |
| аудитор | этап и проверяемая цель `{{stage_goal}}`, отчёт исполнителя `{{executor_report}}`, gate `{{gate_evidence}}`, незакрытые замечания `{{open_findings}}`, разрешённые пути `{{allowed_paths}}`, ожидаемые результаты `{{deliverables}}`, формат ответа `{{audit_contract}}` |
| исполнитель | `{{stage_goal}}`, `{{allowed_paths}}`, `{{deliverables}}`, замечания предыдущего аудита `{{previous_review}}`, `{{gate_evidence}}` |

Раздел цели выводит код, название и проверяемую цель (`objective`) карточки.
Поэтому правка цели в карточке доходит до агентов, даже если подробный текст
этапа её не повторяет.

Раздел, подстановка которого уже есть в тексте, не повторяется. Порядок
итогового промпта:
1. текст этапа;
2. добавленные разделы;
3. прошлый отчёт исполнителя того же этапа;
4. указания оператора;
5. инструкция «ИТОГ».

Встроенные шаблоны уже содержат все разделы, поэтому для этапов без собственных
текстов промпт не меняется.

Подстановки заполняются за один проход: текст отчёта, цитирующий `{{...}}`,
остаётся как есть. Планировщик предупреждён, что эти поля необязательны и
контекст добавляется автоматически.

## Deterministic gate

Команды запускаются кодом PromptPilot в `repository_path`, а не LLM-аудитором.
На Windows используется Windows PowerShell, на POSIX — `/bin/sh`. Ненулевой exit
code или timeout после успешного закрытия owned process tree дают `FAIL`.
Проверенная ошибка до вызова process factory даёт `HUMAN_REQUIRED`.
Последние 4000 символов вывода каждой команды сохраняются в append-only event.

Если gate включён, но список команд пуст, результат — `HUMAN_REQUIRED`:
автоматический PASS без доказательств запрещён. Настройте команды проверки
или явно отключите gate для миссии, где такая проверка не требуется.

Автоматический gate выполняется последовательно для одной миссии. Отдельный
SQLite lock в `<PP_DATA_DIR>/gate-locks/` удерживается до записи результата;
основная БД не заблокирована на время shell-команды. Разные миссии могут
выполнять проверки одновременно. Lock-файлы нельзя удалять или пересоздавать:
это может разделить владельцев блокировки. При потере или повреждении уже
использованного файла запуск отклоняется. Гарантия относится к процессам с
общими основной БД и локальным data-root, не к разным машинам или произвольной
сетевой файловой системе.

До process factory в основной БД фиксируется `STARTED` с execution ID и
снимком раунда, стадии, завершённого executor run, его input/output digests,
рабочего каталога, команд и shell argv. Команды упорядочены, повторы удалены;
конфигурация не перечитывается между запусками. Перед следующей командой
проверяется актуальность снимка; смена контекста останавливает оставшиеся
команды. Только подтверждённое окончание owned lifetimes позволяет сохранить
`SETTLED`; решение, событие gate и `APPLIED` затем записываются атомарно.
После сбоя уже сохранённое `SETTLED` применяется без повторного shell-запуска.

Сбой между `STARTED` и `SETTLED`, исключение factory после возможного spawn
или неоднозначное закрытие process tree дают `UNKNOWN`. Даже если процесс
не успел запуститься, после перезапуска это нельзя доказать. Один
`gate.execution_unknown` содержит execution ID и recovery nonce; повторный
`advance` не запускает команду и не добавляет события. Возраст записи и PID
не дают права на повтор. Изменение конфига, ручной `/gate`, human input
(включая note, resume и checkpoint restart), dispatch и создание нового раунда
отклоняются при любом unresolved исполнении всех версий. Cancel сохраняет
журнал и терминальное состояние, но не является доказательством cleanup.
Удаление истории исполнения запрещено.

### Инженерное восстановление UNKNOWN

Инженер должен самостоятельно убедиться, что прежние процессы остановлены,
и проверить последствия команд и состояние checkout. Сервер не может
проверить это утверждение и не обещает откат уже выполненных эффектов.
Обычный resume для этого не подходит. Используйте отдельную операцию:

```http
POST /api/workflows/<id>/gate/recover
Content-Type: application/json

{
  "expected_version": 17,
  "execution_id": "<точный ID из gate.execution_unknown>",
  "recovery_nonce": "<точный nonce из того же события>",
  "reason": "Проверены остановка прежних процессов, последствия и checkout",
  "acknowledge_gate_effects_reviewed": true
}
```

Или CLI с теми же обязательными полями:

```bash
pp workflow recover-gate <id> --execution-id <execution-id> \
  --recovery-nonce <nonce> --expected-version 17 \
  --reason "Проверены процессы и последствия" --acknowledge-gate-effects-reviewed
```

Точная версия, ID, одноразовый nonce, непустая причина и acknowledgement
обязательны. Занятый lock, устаревшие или повторные данные дают conflict.
В журнале сохраняются UNKNOWN-событие, операторское утверждение и
`cleanup_confirmed=false`; оно не превращается в машинное доказательство.
Старое исполнение становится `RESOLVED`, миссия возвращается в `GATING` того
же раунда без повторного executor. Следующий `advance` выполняет новую
проверку с новым execution ID; старый PASS не переносится. Отменённые и иные
терминальные миссии эта операция не возобновляет.

### Чекпоинты этапов

`automation.stage_checkpoint` по умолчанию выключен. При включении после
зелёного gate и принятого ревью фиксируются только доказанные пути этапа.
Чекпоинт сохраняет проверенные HEAD, ветку, байты и режимы файлов; обновляет
ветку через Git CAS и оставляет чужие staged-файлы в индексе. Изменившиеся
после приёмки байты не принимаются по старому PASS. Подготовка объектов не
блокирует общую очередь SQLite; отмена во время подготовки запрещает публикацию.
Заметки текущего этапа сохраняются при сбое чекпоинта и перезапуске приёмки.
Они удаляются только вместе с успешным переходом дальше; общая память миссии
и заметки следующего этапа сохраняются.

При обычной ошибке миссия остаётся у человека; resume повторяет барьер.
Частичная публикация восстанавливается по `<git-dir>/promptpilot-checkpoints/<id>/`:
там лежат `intent.json`, `index.before` и `index.after`. Известная комбинация
HEAD и индекса завершается без второго коммита; неизвестная требует осмотра.
После аварийного завершения процесса возможны stale `index.lock`, `HEAD.lock`
или lock текущей ветки. Автоматически они не удаляются: сначала убедитесь,
что записанный процесс и его Git-потомки завершены, сверьте HEAD, ветку,
хеши индекса и intent; удаляйте только подтверждённые lock этой операции.
Чужие lock и изменения не сбрасываются. Это восстановление после сбоя
процесса; гарантия сохранности при внезапном отключении питания не заявляется.
В linked worktree `.git` — файл, поэтому реальный `<git-dir>` находите командой
`git rev-parse --absolute-git-dir`, индекс —
`git rev-parse --path-format=absolute --git-path index`. Lock индекса имеет
тот же путь с суффиксом `.lock`; пути HEAD и общей ветки проверяйте через
`git rev-parse --git-path HEAD` и `git rev-parse --git-path refs/heads/<ветка>`.
Пользовательские clean-фильтры/working-tree-encoding и нестандартные типы
файлов требуют отдельного адаптера и отклоняются.

Если содержимое изменилось и прежний PASS нужно отозвать, используйте
`POST /api/workflows/<id>/human-input`: `restart_checkpoint: true`, актуальный
`expected_version`, наблюдаемый полный SHA в `checkpoint_head`, причина в
`text` и при необходимости новые инструкции в `note`. Этот запрос несовместим
с `resume: true`: он переводит этап в `revision_required`, закрывает старый
pending отдельным событием и отзывает прежний PASS. После обычного resume с
новой версией снова выполняются executor, gate и независимый reviewer.
Ограничения числа раундов сохраняются. Legacy-чекпоинт без доказательств
перезапускается только таким явным запросом с подтверждённым HEAD; аудит
отмечает `legacy_ambiguous`, не объявляя неизвестный старый коммит принятым.
Уже опубликованный известный коммит сначала завершает обычный resume recovery;
неизвестные состояния HEAD/индекса автоматически не перезапускаются.

## Права ролей

У каждой роли в `config.roles` есть поле `rights` — те же уровни, что у обычной
задачи (`none`, `read`, `write`, `full`, см. README «Права задачи»). Например,
исполнитель правит файлы, но не запускает команд, а аудитор только читает:

```json
"roles": {
  "executor": {"provider": "claude", "rights": "write", "worktree": true},
  "reviewer": {"provider": "claude", "rights": "read"}
}
```

Аудитору `full` запрещён — как и `skip_permissions`. Deterministic gate
запускает PromptPilot сам, поэтому исполнителю с `write` тесты запускать не нужно.

## Автоматические остановки

Человек получает мяч, когда:

- аудитор вернул `HUMAN_REQUIRED` или нарушил машинный контракт;
- исчерпан `max_rounds`;
- исчерпан `max_revisions_per_stage` или индивидуальный лимит этапа;
- planner вернул невалидный `stage-plan-v1` контракт;
- provider/session настроены некорректно;
- semantic conflict не позволяет принять PASS (например, остался открытый
  blocker/high finding);
- команда gate не может быть запущена из-за среды;
- превышен защитный лимит внутренних переходов state machine.

После перезапуска worker выполняет sync незавершённых workflow и продолжает
разрешённый автоматический переход. Все переходы используют optimistic version
и idempotent task/run projection.

### Указание агенту при продолжении

В поле «Что передать агенту» кнопки «Продолжить» (или `note` в
`POST /api/workflows/{id}/human-input`, `pp workflow input <id> <текст> --resume
--note "..."`) пишется то, что должен узнать следующий запуск. Указание
попадает в промпт следующего исполнителя и следующего аудитора — каждому один
раз — отдельным блоком `<указания-оператора>`, который главнее инструкций
раунда. Шаблон роли может сам поставить указания в нужное место плейсхолдером
`{{human_input}}`.

Поле `text` — это запись решения в журнал. Агентам оно не передаётся: туда же
пишет свои служебные строки автоматика («Автоматический новый раунд…»).
Указание, данное при отказе по лимиту раундов, не теряется и уйдёт в запуск,
который начнётся после увеличения лимита.

## Экспорт для анализа и статьи

В карточке есть кнопки `Экспорт JSON` и `Экспорт Markdown`. Endpoint:

```text
GET /api/workflows/{id}/report?format=json
GET /api/workflows/{id}/report?format=markdown
```

JSON содержит конфигурацию, план, этапы, раунды, attempts, findings, artifacts, append-only
timeline и вычисленные показатели: количество ручных/PromptPilot-раундов,
попыток planner/executor/reviewer, статусов этапов, PASS/FAIL gate,
revision/PASS аудитов, пауз, провайдеров, моделей,
время агентов и полное elapsed time. Это факты из SQLite; утверждения старых
агентских отчётов остаются отдельно в raw run output/events.

## Текущие границы W3

- физический read-only checkout аудитора ещё не обеспечен; запрет записи задан
  ролью и отсутствием `skip_permissions`;
- план выполняется как безопасная последовательность; произвольный DAG и
  параллельное выполнение независимых этапов пока не поддерживаются;
- автоматический merge/release не выполняется;
- этап вне PromptPilot принимает текстовый результат; вложения, прямые
  интеграции с внешними сервисами и параллельные внешние этапы — позже;
- gate-команды выполняются синхронно в worker-потоке;
- токены и стоимость берутся общей подсистемой PromptPilot и пока не связываются
  с workflow report как отдельная бухгалтерия.



## Бюджет возвратов и явные настройки

Явно сохранённый `planning.max_revisions_per_stage` имеет приоритет над `max_revision_rounds` этапа, включая одноэтапный workflow без плана. Если поля в конфигурации нет, используется лимит этапа; при отсутствии обоих — 3. Отсутствующее поле остаётся отсутствующим после сохранения, чтения и перезапуска, а не превращается в явное значение по умолчанию.

Повышение бюджета в настройках позволяет продолжить остановленный этап, даже если модель закрепила меньший лимит в плане. Общий `limits.max_rounds` сохраняется и по-прежнему ограничивает автоматические раунды. Существующие сохранённые значения не удаляются автоматически: старый нормализованный JSON не содержит сведений об их первоначальном источнике. Выбранное значение в таком JSON учитывается как настройка; для возврата к лимиту этапа передайте конфигурацию без `planning.max_revisions_per_stage`.


Пустое поле «Возвратов на один этап» означает наследование из плана (или 3). Сохранение других настроек не создаёт явный лимит. Если очистить ранее заданное число, сохранение удалит override и вернёт наследование.
