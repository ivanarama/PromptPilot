# Восстановление проверки сданного результата

Если проверяющий завершился по техническому таймауту, повторять исполнение
задачи не требуется. В карточке показаны причина и кнопка **Повторить только
ревью**. Она повторно проверяет сданный результат техническим gate и запускает
новую независимую попытку ревью того же раунда. Старые результаты, ошибки,
патч и замечания сохраняются.

Автоматический повтор после точного машинного таймаута включается владельцем
в `roles.reviewer.technical_review_retries`: по умолчанию `0`, допустимо `0–2`.
Лимит считается по раунду и сохраняется при перезапуске. Для работы также
нужны включённые automation, auto_gate, auto_dispatch_reviewer, auto_apply_review.
Пустой отчёт, неопределённая ошибка, отмена, незавершённый процесс, запрос
оператору и `HUMAN_REQUIRED` не являются основанием автоматического повтора.
Workorder использует отдельную процедуру восстановления.

`roles.reviewer.task_timeout` задаёт бюджет именно проверки. `null` наследует
общий timeout экземпляра; это может оказаться существенно меньше требуемого
времени на чтение и тесты. Не устанавливайте `0` ради устранения остановки:
подберите конечный лимит по наблюдаемой работе и ограничьте число повторов.

Доступ к источникам проверяющего зависит от настройки его CLI и sandbox.
Если задача требует сверки GitHub, заранее проверьте доступ из той же среды.
Не используйте full rights или отключение sandbox как замену сетевой настройке.
Настраивайте отдельного провайдера/профиль для нужного проекта. Сохраняйте
независимость автора и проверяющего; сетевой сбой не означает успешное ревью.

Для owner API повтор доступен через
`POST /api/workflows/{id}/review-retry` с `expected_version` и `reason`.
Устаревший запрос получает 409. Повтор не может переоткрыть уже принятый
результат, обойти ожидающий checkpoint, вопрос оператору или активное ревью.
Клиентский MCP постановки задач не получает права вызывать этот owner endpoint.
