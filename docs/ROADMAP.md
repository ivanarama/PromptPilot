# Roadmap: интеграция с herdr и мульти-машинное выполнение

Документ фиксирует план развития PromptPilot: интеграция с [herdr](https://github.com/herdrdev/herdr)
(терминальный мультиплексор для AI-агентов) и распределение задач по нескольким машинам.
Основная платформа — **Ubuntu/Linux** (Windows-артефакты — tray, .exe — вторичны).

## Почему herdr

PromptPilot и herdr почти идеально комплементарны:

| | PromptPilot | herdr |
|---|---|---|
| Очередь, планирование, retry, recurrence | ✅ | ❌ (нет и не планируется) |
| Telegram-управление и уведомления | ✅ | ❌ |
| Живые интерактивные сессии агентов | ❌ (headless `-p`) | ✅ |
| Состояние агента (`idle/working/blocked/done`) | ❌ | ✅ |
| Наблюдаемость / возможность вмешаться | ❌ | ✅ (attach, в т.ч. по SSH) |

Ключевая ценность связки: задача, упёршаяся в permission prompt, не умирает и не требует
`--dangerously-skip-permissions` — агент переходит в `blocked`, человек получает уведомление,
подтверждает в панели и задача продолжается.

## Фазы интеграции с herdr

### Фаза 1 — нативный исполнитель ✅ (2026-08-04)

Изменено ядро: `worker.py`, `config.py`, `db.py`, `bot.py`; новый модуль
`promptpilot/herdr_exec.py`.

- Провайдер с `"executor": "herdr"` в providers.json (вместо bash-обёртки) —
  worker ведёт сессию через `herdr` CLI напрямую (`run_in_herdr()`).
- Статус `blocked` → задача остаётся `running`, в таблицу `notifications`
  пишется сообщение с pane id; бот доставляет его в Telegram (loop каждые 10 с).
- Rate limit внутри сессии (текстовые баннеры) → стандартный backoff-retry.
- Таймаут задачи выполняется на стороне herdr (`--timeout`, чистый abort).
- Retry на `agent_pane_busy` (shell свежей панели поднимается асинхронно)
  и на `agent_prompt_stalled` (с защитой от двойной отправки).
- `detached` для herdr-провайдера: промпт отправлен → задача completed,
  панель с работающим агентом остаётся открытой.
- `"keep_pane": true` у провайдера (или `PP_HERDR_KEEP_PANE=1`): задача
  выполняется как обычно (результат в базу, уведомления), но панель
  остаётся открытой для продолжения работы; агент переименовывается в
  `t<id>` (выходит из `pp-t*`-неймспейса — Telegram-мост начинает следить
  за продолженной сессией), вкладка — в `pp-kept-<id>`.
- `env`-блок провайдера пробрасывается в панель (`tab create --env`).
- Crash-recovery: перед запуском закрываются осиротевшие панели прошлых
  попыток этой задачи (`pp-t<id>-*`).
- `run_in_herdr()` не бросает исключений (worker-цикл защищён от крэш-лупа);
  `pp purge` чистит и доставленные уведомления.

Проверено e2e: обычная задача, blocked-задача с уведомлением и ручным
подтверждением, detached. Ограничения (принятые): нет cost/session_id для
herdr-задач (интерактивный режим не отдаёт stream-json); SIGKILL оставляет
панель живой (до следующего запуска той же задачи); время в `blocked` не
ограничено таймаутом — это ожидание человека, by design.

### Фаза 2 — Telegram-мост для herdr ✅ (2026-08-04)

Бот наблюдает за **всеми** агентами herdr (не только задачами PromptPilot)
и шлёт уведомления, когда агент заблокирован диалогом или завершил работу
незамеченным (`done` в herdr = «idle после незамеченной фоновой работы»).

- Реализация: поллинг `herdr agent list` каждые `PP_HERDR_WATCH_INTERVAL`
  (10 с) в `_herdr_watch_loop` бота. Событийный вариант через `events.subscribe`
  отвергнут: подписка `pane.agent_status_changed` в socket API — только
  per-pane (требует конкретный `pane_id`), глобального wildcard нет, пришлось
  бы отслеживать жизненный цикл панелей. Поллинг проще, использует стабильный
  CLI, а интервал заодно служит дебаунсом: диалоги, которые пользователь сам
  разрешает за секунды, работая в herdr, в уведомления не попадают.
- Кнопки под уведомлением: «✅ Подтвердить (Enter)» (`agent send-keys`),
  «📺 Экран» (`agent read --source visible`), «✍️ Ответить» (`agent prompt`).
- Агенты PromptPilot-задач (`pp-t*`) исключены — о них уведомляет worker.
- Выключается `PP_HERDR_WATCH=0`; уведомления идут всем авторизованным
  пользователям бота (`tg_users.json`).

Это уникальная ниша: в экосистеме herdr Telegram-уведомлений нет, а его аудитория
(24k звёзд) — люди, которые «detach and walk away».

## Задачи в открытую herdr-сессию ✅ (2026-08-05)

Пользовательский сценарий: в herdr уже открыта живая сессия (оставленная
задачей `pp-kept-N` или запущенная вручную) — хочется из Web UI/бота отправить
в неё промпт **как задачу**: с очередью, расписанием (`в 09:00 подведи итоги`),
recurrence, результатом в базе и уведомлением.

Реализовано по дизайну ниже; проверено e2e (промпт в живую сессию,
результат в базе, панель не тронута; закрытая панель — понятная ошибка).

Дизайн:
- Поле задачи `herdr_target` (pane id `w9:p2` или имя агента) + миграция.
- Псевдо-провайдер `herdr-session` (executor herdr, без kind): в
  `run_in_herdr` target-режим — без tab create/agent start; проверка
  `agent get <target>` (нет агента → понятная ошибка «панель закрыта?»),
  submit с retry, chunked-ожидание с blocked-уведомлением и отменой,
  чтение результата; панель НЕ закрывается и не переименовывается (не наша).
  model/skip-permissions в target-режиме не применимы.
- API `GET /api/herdr/agents` — список живых агентов (`herdr agent list`:
  имя, pane, вид, статус, заголовок) для выпадашки.
- Web UI: при выборе `herdr-session` — выпадашка живых сессий вместо модели.
- Бот: тот же список кнопками; ✍️-кнопка моста остаётся мгновенной, а
  провайдер `herdr-session` — путь «запланировать в сессию».
- Побочный эффект: цепочки задач в одну сессию = «💬 Ответить» для herdr-задач
  (которого нет из-за отсутствия session_id).

## Мульти-машинное выполнение — варианты

### Вариант 1 — SSH-выполнение ✅ (2026-08-05): реестр машин

Реализовано в двух слоях:
- `scripts/pp-ssh-run` — низкоуровневая обёртка (cmd-шаблон провайдера);
- **реестр машин** (`machines.json`, UI «🖥 Машины», `/api/machines`,
  шаг «Где выполнить?» в боте): машина — отдельное измерение задачи
  (`tasks.machine`), автопроба возможностей по ssh (`probe_machine`),
  выполнение `ssh host bash -lc ...` с basename-резолвом и пробросом
  env провайдера. Проверено e2e через localhost (cost/session работают).

Ограничения v1: detached — только локально; рабочая директория удалённой
headless-задачи = $HOME машины. (herdr-провайдеры на машинах — вариант 2 ниже.)

Исходный план:

Центральная очередь (worker, Web UI, бот) на одной машине; удалённые машины —
провайдеры вида `pp-ssh-run <host> {prompt}` (обёртка обязательна: ssh склеивает
argv, промпт с пробелами развалится — надёжнее передавать промпт через stdin в
`claude -p`).

- ✅ stream-json проходит через ssh насквозь → cost/session_id/rate-limit работают.
- ✅ Выбор машины = выбор провайдера (уже есть в боте и UI). Ядро не меняется.
- ❌ Очередь остаётся последовательной (одна задача за раз на всю систему).
- Требования: ssh-ключи, claude CLI на каждой машине. Оценка: ~полдня.

### Вариант 2 — SSH + herdr на удалённых машинах ✅ (2026-08-05)

Надстройка над вариантом 1: herdr-провайдеры перестали быть локальными —
herdr CLI машины вызывается по ssh, панель с агентом живёт на ней,
вмешательство — `herdr --remote <host>`.

Реализация:
- `herdr_exec`: `herdr_argv(args, host)` — один хелпер строит либо локальный
  вызов, либо `ssh <opts> host bash -lc '<quoted>'` (двойное квотирование:
  ssh склеивает argv в одну строку); `host` протянут во все вызовы
  (`run_in_herdr`, `_wait_settled`, `_close_stale_tabs`). Удалённый herdr
  server поднимается через `nohup herdr server &` (иначе ssh висит), у
  удалённых вызовов есть локальный потолок таймаута (`REMOTE_CALL_TIMEOUT`),
  бинарь резолвится по login-shell PATH машины (basename).
- `worker`: машина резолвится в host до ветвления executor'а; herdr-ветка
  получает host, в blocked-уведомлении — машина и `herdr --remote <host>`.
- `probe_machine`: herdr-провайдер объявляется доступным, если на машине есть
  `herdr` **и** CLI его `kind` (`herdr-session` — только herdr).
  Старые записи `machines.json` нужно один раз перепроверить.
- API `GET /api/herdr/agents?machine=<name>` и выпадашка живых сессий в Web UI
  — по выбранной машине; неизвестная машина → 404.
- Telegram-мост наблюдает за агентами на всех машинах с herdr; в callback_data
  кнопок добавлена машина (`hd_enter:<machine>:<pane>`, старый формат читается
  как локальный), в тексте уведомления — имя машины.
- Заодно: на `agent_prompt_stalled` сначала отправляется `send-keys enter`
  (текст уже в поле ввода — некоторые сборки агентов глотают submit после
  вставки) и факт отправки проверяется по `state_change_seq`; повторная
  отправка промпта осталась запасным вариантом. Раньше ретрай печатал промпт
  второй раз.

Проверено e2e через машину `vm05-loop` (localhost по ssh): пять задач
`claude-herdr` выполнены рабочим воркером, `herdr-session` в удалённую сессию,
keep-pane, список агентов машины через API и async-хелперы бота. A/B локально
и по ssh даёт идентичное поведение.

**Windows-машины** (2026-08-06). У herdr есть нативная сборка под Windows
(`install.ps1`, канал preview) — WSL не нужен, но наш ssh-слой говорил только
на POSIX. Появился модуль `promptpilot/remote.py`: `Remote(host, shell)` и
`ssh_command`/`ssh_script`, которые строят либо `bash -lc '<quoted>'`, либо
`powershell -EncodedCommand <base64/UTF-16LE>`. Кодирование выбрано потому, что
виндовый sshd пропускает командную строку через `cmd.exe`, где кавычки не
выживают; в base64 нет спецсимволов cmd. Диалект определяется автоматически
(`detect_shell`: сначала posix-проба, затем powershell) и хранится в
`machines.json` полем `shell`; записи без него читаются как posix.
`probe_machine` теперь возвращает `(providers, shell)` и на Windows ищет CLI
через `Get-Command`, `_start_server` поднимает сервер через `Start-Process
-WindowStyle Hidden`, env провайдера превращается в `$env:K='V'`.
Windows-машина с Git Bash в DefaultShell определится как posix — это рабочий
режим, а не ошибка.

Не проверено вживую: сам Windows-путь (нет машины под рукой) — проверено
построение и квотирование команд, а также то, что POSIX-путь после
рефакторинга не изменился (регрессионный прогон задачи через воркер).

- ✅ Blocked-наблюдаемость и вмешательство на любой машине.
- ❌ herdr нужно ставить и держать запущенным на каждой машине
  (сервер поднимается сам, но бинарь и агент должны быть в PATH машины).
- ❌ Очередь всё ещё последовательная.
- Не проверено вживую: blocked-сценарий именно на удалённой машине (код общий
  с локальным, отличаются только текст уведомления и подсказка подключения).

### Вариант 3 — распределённая очередь по HTTP

Воркеры на каждой машине сами тянут задачи из центрального `pp server`.

- ✅ Настоящая параллельность: N машин = N одновременных задач.
- ✅ Устойчивость: недоступная машина просто не берёт задачи.
- ❌ Существенная доработка ядра: auth-токен для API (сейчас API вообще без
  авторизации — наружу открывать нельзя), атомарный claim задачи (сейчас
  SELECT+UPDATE не атомарны для двух воркеров), маршрутизация «задача → машина
  или любая», миграция схемы. Оценка: несколько дней.

### Рекомендованный порядок

1 ✅ и 2 ✅ сделаны. Следующий шаг — когда захочется параллельности: сначала
auth-токен для API (есть, `PP_API_TOKEN`), затем атомарный claim задачи и
pull-воркеры (вариант 3). Артефакты вариантов 1–2 (реестр машин, ssh-обёртка,
host-aware herdr-исполнитель) при переходе к 3 не выбрасываются.

## Свой worktree на задачу + параллельная очередь ✅ (2026-08-12)

Две связанные вещи: изоляция задачи от рабочего дерева пользователя и снятие
ограничения «одна задача за раз».

**Worktree (`worktree: true` у задачи).** Агент работает в отдельном чекауте на
ветке `pp/t<id>`, а не в дереве, где сидит человек. Результат становится веткой
— его можно посмотреть diff'ом, влить или выбросить; retry после rate-limit
возвращается на ту же ветку вместо наслоения на полуизменённое дерево.

- herdr-исполнитель использует родную команду herdr — `herdr worktree
  create --cwd <repo> --branch pp/t<id>`. Ответ той же формы, что у `tab
  create` (`root_pane`/`tab`), поэтому дальше код общий; чекаут виден в UI
  herdr как worktree-workspace, и это бесплатно работает на удалённых машинах.
  Если чекаут прошлой попытки жив — `worktree open` вместо `create`.
  Провайдерский `env` требует отдельного `tab create --workspace` (у
  `worktree create` нет `--env`).
- Обычный (headless) исполнитель делает `git worktree add` сам —
  `promptpilot/worktree.py`, те же git-вызовы работают и по ssh.
  На удалённых машинах не поддержан осознанно: headless-команда по ssh
  выполняется в домашней директории и в чекаут не зайдёт.
- Чекаут не удаляется после задачи (в нём результат). Пустой — без коммитов и
  изменений — herdr-исполнитель убирает за собой. Ветка остаётся всегда.
- `PP_WORKTREE_COPY` (по умолчанию `.env`) переносит в свежий чекаут то, что
  git игнорирует, — иначе задача падает на отсутствующем окружении.

**Параллельность (`PP_CONCURRENCY`).** Пункт «атомарный claim задачи» из
варианта 3 закрыт: `get_next_runnable` берёт write-lock (`BEGIN IMMEDIATE`) и
делает условный `UPDATE ... WHERE status IN ('pending','rate_limited')`, так что
двум претендентам одна задача не достанется. Поверх этого — пул потоков в
worker'е и ключ блокировки на задачу (`worker.lock_key`): рабочая директория,
или herdr-сессия для задач в открытую сессию, или ничего для задач со своим
worktree. Очередь обходит занятое вместо того, чтобы вставать.

Что осталось для варианта 3 (pull-воркеры на каждой машине): владелец задачи и
heartbeat. Сейчас `recover_running()` при старте возвращает в очередь **все**
running-задачи, то есть предполагается ровно один процесс worker'а — второй
отберёт задачи у первого. Это и есть следующий шаг, если параллельности одной
машины перестанет хватать.

## Взято из jira-auto ✅ (2026-08-12)

Внутренний проект jira-auto (корпоративный GitLab) — автономный
решатель задач Jira на `claude -p`, пять параллельных потоков, в проде. Решает
тот же класс задач, что PromptPilot, но дольше и с шрамами. Три вещи оттуда
перенесены (worktree-на-задачу мы придумали параллельно — у них он с самого
начала):

- **Сторож запретов** (`guard.py` у них → `promptpilot/guard.py`). При
  `--dangerously-skip-permissions` диалога нет, значит запрет должен держать
  PreToolUse-хук. Наш вклад поверх их правил — правила пришлось сделать
  устойчивыми к прозе: слово `sudo` в сообщении коммита не должно блокировать
  коммит, а `main-fix` не должен считаться веткой `main`.
- **Срыв по вине среды ≠ провал задачи** (`tick.sh` у них → `worker.env_failure`).
  401/403/5xx и обрыв ответа возвращают задачу в очередь. Их наблюдение, ради
  которого это и сделано: обрыв приходится на конец прогона, работа обычно уже
  сделана и запушена.
- **Порог свободной памяти** (`MIN_FREE_MB` → `PP_MIN_FREE_MB`). Слоты
  параллелизма не знают, потянет ли машина ещё один прогон; на деле она уходит в
  своп, а следом API начинает отказывать.

Не взято: Jira-специфика (метки, захват с разрешением гонки — у нас атомарный
claim в SQLite честнее), модель «поток = systemd-таймер + flock», `netwatch.py`.

Остальное с того разбора тоже сделано (2026-08-12):

1. ✅ **Учёт расхода** (`promptpilot/usage.py`, `pp usage`, `/api/stats/usage`).
   Второй источник — `~/.claude/projects/**/*.jsonl` — закрывает слепоту к
   herdr-задачам. Считаем по сообщениям (там они целые, в отличие от кусков в
   потоковом журнале), кэш отдельными множителями (чтение ×0.1, запись ×1.25),
   задачу узнаём по `session_id`, а без него — по своему worktree. НЕ по
   `working_dir`: его задача делит с человеком, и живая переписка засчитывалась
   задаче — поймали на реальных данных. Нормы пятичасового окна у нас нет:
   `rate_limit_event.utilization` в транскриптах не встречается, поэтому окно
   скользящее, а не доля нормы.
2. ✅ **Приписка к задаче** (`pp note`, поле в карточке, `POST /api/tasks/{id}/note`).
   Живёт при задаче, идёт последним блоком с пометкой «главнее», одноразовая,
   переживает срыв среды и rate limit и не протекает в повторяющиеся копии.
3. ✅ **Структурный вердикт** (`PP_VERDICT=1`, колонка `verdict`). Парсится
   всегда, побеждает последнее совпадение.
4. ✅ **Метка прогона в окружении** (`PP_TASK_ID`, `worker.live_task_ids()`).
   `recover_running(keep_ids=...)` больше не выдёргивает очередь из-под живых
   агентов. Это и был недостающий кусок для нескольких процессов worker'а —
   осталось довесить heartbeat, если понадобится распределённая очередь.

Срез состояния от 2026-11-04, main `a8573f0` (v0.6.0). Это план реализации и

Отметки исходного issue меняются после приёмки соответствующих поставок.

Существующее ядро уже хранит workflow, этапы, раунды, попытки и события,
проверяет `state_version`, владеет задачами и выполняет объявленные gate.
Последовательные flows, заметки `workflow_memory`, оконный выбор провайдера и
pipeline REVIEW решают свои задачи. Новые контракты должны использовать эти
механизмы, сохраняя историю и полномочия конкретной попытки.

### R1 / R2 — несколько ревьюеров

Конфигурация перечисляет именованные слоты, их провайдеров, модели, права,
окна запуска и конечный бюджет. Политика агрегации объявляется явно;
блокирующее замечание не теряется при положительном ответе другого слота.
Каждый результат связан с workflow, раундом, слотом, попыткой, входным
отпечатком и проверяемым HEAD. Смена HEAD сохраняет прежний аудит, но снимает
его применимость к новому результату. Один сохраняемый владелец управляет
допуском к раунду и его итогом.

Приёмка через публичные API: одновременный claim двумя владельцами, дубликат
ответа, рестарт между созданием задачи и связыванием run, смена HEAD,
исчерпание бюджета, недоступный слот и неизвестный исход запуска. Последний
не разрешает запустить заменяющую модель. Провайдер исполнителя не становится
его собственным независимым ревьюером при переключении квот.

### D1 / D2 — граф миссий

Первая поставка принимает версионированное описание узлов и зависимостей,
проверяет уникальность идентификаторов, известность зависимостей, отсутствие
циклов и объявленные границы веток, каталогов и передачи данных. `scaffold`
создаёт описание, `dry-run` показывает порядок, fan-out и точки join.
`status` сообщает фактические версии выбранных workflow/run. Эти операции
не создают задачи, ветки, внешние запросы или разрешения на исполнение.

Исполнение — следующая поставка: узлы используют Core-workflow, имеют
собственные ветки и каталоги; join требует результаты всех объявленных
предшественников. Публикация результата и последовательная интеграция имеют
одного сохраняемого владельца. Неизвестный исход интеграции восстанавливается
по сохранённому намерению и фактическому Git-состоянию.

Приёмка: валидация циклов и отсутствующих узлов, dry-run без побочных действий,
рестарт, конкуренция владельцев, частично завершённый fan-out, отказ одной
ветки, повтор join и отказ в неразрешённой передаче данных между узлами.

### Q1 — ограниченное переключение по квотам

Политика содержит упорядоченный набор допустимых провайдеров, признаки
исчерпания и восстановления квоты, интервал гистерезиса и конечное число
переключений. Сохраняются выбранный провайдер, причина и срок ожидания.
Перед новым запуском повторно проверяются права роли, совместимость адаптера,
окно запуска и независимость ревьюера. Результат неизвестного исхода не
превращается в новый запуск другой модели.

Приёмка: N провайдеров, исчерпание всех квот, восстановление после рестарта,
колеблющийся ответ провайдера, конечность повторов, неизменность исходных прав,
запрет саморевью и отсутствие переключения работающей попытки.

### O1 / O2 — ограниченное наблюдение

Core-контракт выбирает конкретные workflow, run и версии и возвращает
ограниченную сводку и хвост событий с точной атрибуцией. Аутентификация
обязательна; отсутствие или несовпадение разрешённой области даёт отказ.
Параметры размера, курсор и признак усечения входят в ответ. Чтение не меняет
статус, не выдаёт lease и не продолжает выполнение.

MCP-адаптер экспортирует только этот набор операций. Произвольный URL,
произвольная команда и публикация полного текста задач внешнему сервису в
этот контракт не входят. Дополнительная передача данных требует собственной
явной настройки и проверки.

Приёмка: запрос без прав, другой workflow/run/version, ограничение объёма,
смена выбранного запуска, корректный полный и усечённый хвост. Тесты
проверяют отсутствие mutations и запуска провайдера после каждого чтения.

### U1 — интерфейс и наблюдаемый прогресс

Словари RU/EN покрывают выбранный пользовательский путь workflow целиком:
список, карточку, этапы, ожидания, ошибки и управление правами. Язык и
компактность сохраняются в существующих настройках интерфейса. Обновление
данных сохраняет выбранную миссию и клавиатурный фокус.

Состояния этапов и запусков берутся из Core. Счётчик выполненных проверок
показывается только при известных фактических счётчиках; неизвестный объём не
превращается в выдуманный процент. Наблюдения с устаревшим heartbeat явно
помечаются. Настройки прав остаются видимыми и управляемыми.

Приёмка в браузере: оба языка, узкий экран, клавиатура, подписи элементов,
обновление данных, смена workflow и отсутствие подмены прогресса прошлым run.
Проверки одних шаблонов строк не заменяют этот пользовательский сценарий.

### M1 — память с происхождением

Конфигурация задаёт разрешённые относительные пути и лимиты одного файла и
всего набора. Чтение не выходит за объявленный корень через `..`, symlink,
junction или смену корня. Сохранение атомарно и связано с ожидаемой версией
миссии. Запись о происхождении содержит workflow/run/attempt, путь и хеш
прочитанных байтов. Превышение лимита даёт понятный отказ до передачи памяти
провайдеру.

Содержимое памяти считается данными и передаётся в отделённом блоке; оно не
меняет права, разрешённые инструменты или правила независимого ревью.
Приёмка: изоляция двух миссий, рестарт, конфликт версии, смена файла и
ссылок, повреждённая кодировка, лимиты и недоверенные инструкции в памяти.

### E1 — доставка событий между миссиями

Версия схемы, идентификатор события, исходная миссия и версия, разрешённая
подписка, целевая миссия и ожидаемая версия определяют эффект. Его квитанция
фиксируется в той же транзакции, что и изменение Core-состояния. Политика
задаёт допустимые типы событий и конечный бюджет доставки; сырой текст задач
и секреты не становятся полезной нагрузкой по умолчанию.

Приёмка: повтор события, потерянный ответ после commit, рестарт до и после
эффекта, перестановка событий, устаревшая версия источника или цели,
одновременная доставка и неподдерживаемая версия схемы. Неопределённый исход
останавливается на восстановлении, а не вызывает повтор внешнего эффекта.

### Порядок приёмки

Каждая поставка идёт отдельным небольшим PR с критериями из своей строки,
проверками публичных API и необходимыми runtime-проверками. Для слияния нужны
независимое ревью точного HEAD, все обязательные CI и проверка на свежем main.
R1 предшествует R2, D1 и E1 предшествуют D2, O1 предшествует O2. Остальные
срезы можно готовить отдельно, сохраняя эти зависимости и исходные критерии
приёмки issue #217.

### Предлагаемый контракт D1 (ещё не реализован)

Для первой поставки предлагаются команды `pp portfolio validate FILE`,
`pp portfolio scaffold --workflow-id ID [--workflow-id ID ...]`,
`pp portfolio dry-run FILE` и `pp portfolio status FILE`. Для scaffold можно
выбрать `--layout parallel` или `--layout sequential`. Предлагаемый вывод —
JSON в stdout; сохранение файла описания выполняет вызывающая сторона.

Предлагаемые операции API: POST `/api/portfolios/validate`, `/scaffold`,
`/dry-run`, `/status` под существующей аутентификацией Core. Вход scaffold —
`workflow_ids` и `layout`; остальных операций — описание графа:

```json
{
  "version": 1,
  "data_transfer": "none",
  "nodes": [
    {"key": "prepare", "workflow_id": "EXISTING_WORKFLOW_ID", "expected_version": 0, "depends_on": []},
    {"key": "check", "workflow_id": "ANOTHER_WORKFLOW_ID", "expected_version": 0, "depends_on": ["prepare"]}
  ]
}
```

Предлагаемый лимит — от 1 до 32 различных workflow в графе. `validate` должен
проверять только структуру и зависимости, работать без базы и возвращать
отпечаток описания. Остальные операции должны читать существующий Core в
одной read-only SQLite-транзакции. `dry-run` и `status` требуют точного
`expected_version`; необязательный `expected_run_id` должен принадлежать
выбранному workflow. Предлагаемые ответы: отсутствующий workflow — 404,
изменившаяся версия, чужой run или совпадающая объявленная пара
repository/branch — 409, недоступная база — 503 без её создания.

Предлагаемый ответ содержит слои графа, последовательность предполагаемой
интеграции, точки join и состояния выбранных workflow/run.
`dispatch_authorized` должен быть `false`, `execution` — `not_implemented`;
политика передачи данных — только `none`. Для D1 предлагается не сохранять
портфель в отдельную таблицу: после рестарта клиент предъявляет то же
описание и получает проверенный снимок. Содержимое промптов, памяти и
артефактов в этот контракт не входит.

Проверка repository/branch в D1 относится к объявленным путям, а не к
физической изоляции checkout через Git и ссылки файловой системы. Создание
веток, исполнение узлов, восстановление владельца, передача артефактов и
публикация результата относятся к следующей поставке D2.

Этот план не меняет производственные установки, политики прав, флаги,
Windows-конвейер или внешние сервисы. Приёмка отдельных PR #235/#236 не
закрывает семь направлений исходного issue целиком.
