# Архитектура PromptPilot

Карта для того, кто впервые открывает код: что здесь ядро, что надстройки,
как они связаны и где проходят границы доверия. Подробности каждой части — в
README и документах `docs/`.

> Часть описанного приходит открытыми PR: права задачи (#134), маршруты
> заявок (#135, #136), внешние этапы workflow (#137), защита API без токена
> (#125). Пока они не влиты, соответствующих модулей и полей на `main` нет.

## Одна мысль

**Ядро — очередь задач и воркер, который запускает любой AI CLI.** Всё
остальное — надстройки, которые *ставят задачи в эту очередь* и читают их
результат, а не запускают агентов сами. Поэтому у всех сценариев общие
провайдеры, права, таймауты, повторы, уведомления, учёт расхода и
восстановление после перезапуска.

```
            Web UI · REST API · Telegram-бот · CLI · трей
                               │
   ┌───────────────┬───────────┼─────────────┬──────────────┐
   │ Workflow      │ Маршруты  │ Конвейер    │ 1С-обработки │   надстройки
   │ Orchestrator  │ заявок    │ проектов    │ (/epf)       │
   │ workflows.py  │ flows.py  │ project_pipeline.py        │
   │               │           │ pipeline_*.py│ epf_tools.py │
   └───────┬───────┴─────┬─────┴──────┬──────┴──────┬───────┘
           └─────────────┴─ задачи ───┴─────────────┘
                               │
            ┌──────────────────▼──────────────────┐
            │ очередь задач (SQLite) → worker.py  │   ядро
            │ провайдеры, права, guard (config.py,│
            │ guard.py) → процесс CLI агента      │
            │ (process_tree.py, herdr_exec.py,    │
            │ remote.py)                          │
            └─────────────────────────────────────┘
```

## Ядро

| Модуль | Что делает |
|---|---|
| `db.py` | вся SQLite: схема и миграции, очередь задач, серии повторов, уведомления, настройки, хранилище workflow и маршрутов. WAL, `_connect(immediate=True)` для «прочитал — решил — записал» |
| `models.py` | Pydantic-модели задач, workflow, прав |
| `config.py` | `.env`, провайдеры (встроенные + `providers.json`), `build_cmd` — команда запуска CLI, права задачи (`rights_args`) |
| `worker.py` | цикл воркера: взять задачу, собрать промпт, запустить процесс, дождаться, записать итог (`ИТОГ: …`), повторы и rate limit, heartbeat, восстановление зависших |
| `process_tree.py` | процесс задачи в своём Job Object (Windows) / группе: таймаут и отмена гасят всё дерево |
| `guard.py` | PreToolUse-хук Claude: режет катастрофические команды у задач без диалога |
| `herdr_exec.py`, `remote.py`, `worktree.py` | исполнение в живой herdr-сессии, на другой машине по SSH, в своём git worktree |
| `usage.py`, `version.py`, `tg_auth.py` | расход за окно лимита, проверка обновлений, авторизация Telegram по телефону |

**Жизненный цикл задачи:** `pending` → `running` → `completed` / `failed` /
`cancelled`, или `rate_limited` с возвратом в очередь. Попытка задачи
отличается по `started_at` (attempt fencing): итог старой попытки не
перезапишет новую. Повторяющиеся задачи — серии (`task_series`), следующее
вхождение создаётся после завершения предыдущего.

**Права задачи** (`rights`: `none` / `read` / `write` / `full`) переводятся в
флаги каждого CLI (`config.rights_args`). Провайдер, который так не умеет,
задачу не запустит — fail closed.

## Надстройки

**Workflow Orchestrator** (`workflows.py`, [спецификация](WORKFLOW_ORCHESTRATOR_SPEC.md),
[руководство](WORKFLOW_AUTOMATION_GUIDE.md)) — большая инженерная задача:
planner → этапы → для каждого раунды «исполнитель → deterministic gate →
независимый аудитор» до PASS. Состояние — строки `workflows`, `workflow_stages`,
`workflow_rounds`, `workflow_runs`, журнал `workflow_events` (только
дописывается), переходы — по `state_version`. Исполнитель и аудитор — обычные
задачи очереди; этап можно отдать вовне (run без задачи, статус
`awaiting_external`).

**Маршруты заявок** (`flows.py`, `flow_connectors.py`, [FLOWS.md](FLOWS.md)) —
запросы извне (почта, issues GitLab) по шагам из JSON-файла: агент с правами,
решение человека, команда, публикация, действия в GitLab, ответ письмом.
Доверие (`owner` / `team` / `client` / `public`) проверяется при загрузке
маршрута. Заявки — `flow_items` (переходы — compare-and-set по `version`),
журнал — `flow_events`. Процесс — `pp flows run`.

**Конвейер проектов** (`project_pipeline.py` — `pp pipelinectl`,
`pipeline_insights.py`, `pipeline_board.py`, `pipeline_watch.py`,
`pipeline_item_holds.py`, `fallback_handoff.py`) — очереди работ по
GitHub-проектам (onebase): профили, стадии review/merge с арендами (leases),
единый барьер, бюджет GitHub API, отчёты. Живёт внутри воркера — см. точки подключения ниже.

**1С-обработки** (`epf_tools.py`, `/epf` в боте) — доработка внешних
обработок 1С: выгрузка, задача агенту, сборка.

Сценарии в `scripts/` (`inbox`, `oneservice`) — отдельные программы поверх
REST API; маршруты заявок (#135, #136) повторяют их на общем ядре, и после
перехода скрипты можно выключить.

## Точки подключения конвейера к воркеру

Конвейер — единственная надстройка, которая участвует в *планировании*
очереди, а не только ставит задачи. Все вызовы — из `worker.py`, только для
задач серии (`task.series_id`), в `try/except`: без профилей конвейера они
ничего не делают, а сбой конвейера не останавливает обычную очередь.

| Где в воркере | Вызов `pipeline_insights` | Контракт |
|---|---|---|
| `_claim_next_task` | `worker_lane_policy()`, `worker_budget_fairness_policy()`, `worker_lane_rank(task, policy, busy)` | какую из готовых задач взять и в какой «полосе» |
| `_execute_task_body` до запуска | `dispatch_gate(task)` | `None` или `{"action": "defer" / "complete_empty" / "restrict_prompt", "reason", …}` — отложить, закрыть без агента, сузить промпт |
| `_execute_task_body` до запуска | `execution_route(task, prompt, working_dir, retain_budget=True)` | `{"action": "run" / "block" / "defer", "mode", …}` — допуск к исполнению, бюджет |
| `_execute_task_inner`, `finally` | `release_execution_admission()` | вернуть зарезервированный бюджет |
| после успешного итога | `after_task_completed(task, verdict)` | разбудить зависимые стадии |
| повтор серии | `_matching_queue(task)` | выключатель повторяющегося блокера |

Со стороны базы конвейер держит `pipeline_target_reservations` (их
освобождают `mark_*` задачи) и отметки удержаний (`pipeline_item_holds`).

Выносить эти вызовы в отдельный реестр хуков сейчас не стали: конвейер
активно развивается ровно в этих местах, а реестр был бы переименованием,
которое конфликтует с каждым изменением. Когда контракт устоится, таблица
выше и есть готовый протокол `TaskHooks`.

## Интерфейсы и процессы

| Процесс | Команда | Что делает |
|---|---|---|
| сервер | `pp server` | REST API (`api.py`, FastAPI) и Web UI (`static/index.html` — один файл); фоновый сэмплер снимков конвейера |
| воркер | `pp worker` | исполняет очередь (`PP_CONCURRENCY` задач одновременно, не больше одной на рабочее дерево) |
| бот | `pp bot` | Telegram (`bot.py`): задачи, уведомления, кнопки решений маршрутов, отчёты |
| маршруты | `pp flows run` | входы и шаги маршрутов заявок |
| трей | `pp` / `pp tray` | запускает и сторожит остальные (`tray.py`) |

`start.ps1` / `stop.ps1` делают то же без трея, `docker-compose.yml` — в
контейнерах. Все процессы делят одну базу `~/.promptpilot/promptpilot.db`;
общение между ними — через неё (очередь, уведомления, флаги отмены).

## Границы доверия

- **API.** Без `PP_API_TOKEN` сервер слушает только loopback и отвечает только
  своим именам хостов, а небезопасные запросы — только со своего Origin
  (защита от DNS rebinding и соседних портов, #125). С токеном — Bearer или
  Basic.
- **Задача.** Что можно агенту — `rights`; `guard` режет катастрофические
  команды у задач без диалога; процесс задачи изолирован своим деревом.
- **Текст извне** (письма, формы, issues) — только в маршрутах: доверие
  маршрута ограничивает права агентов, текст не попадает в командную строку и
  пути, в промпте обрамлён как данные, публикуется без ссылок.
- **Telegram.** Кнопки и команды — только авторизованным по телефону, в личном
  чате (`require_auth`).

## Тесты и сборка

`pytest` — весь набор (`tests/`), изолированная база (`isolated_db`); CI
(`.github/workflows/test.yml`) — Python 3.10 и 3.12 на Linux и Windows (ruff —
с #131). `pp.spec` / `build.ps1` — сборка `pp.exe`
через PyInstaller.
