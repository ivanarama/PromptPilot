# Архитектура PromptPilot

Карта для того, кто впервые открывает код: что здесь ядро, что надстройки,
как они связаны и где проходят границы доверия. Описано то, что есть в `main`;
подробности каждой части — в README и документах `docs/`. PR, который меняет
одну из частей, правит и этот файл.

## Одна мысль

**Ядро — очередь задач и воркер, который запускает любой AI CLI.** Всё
остальное — надстройки, которые *ставят задачи в эту очередь* и читают их
результат, а не запускают агентов сами. Поэтому у всех сценариев общие
провайдеры, права, таймауты, повторы, уведомления, учёт расхода и
восстановление после перезапуска.

```
         Web UI · REST API · Telegram-бот · CLI · трей
                               │
     ┌──────────────┬──────────┴──────────┬─────────────────────┐
     │ Workflow     │ Конвейер проектов   │ 1С-обработки (/epf) │  надстройки
     │ Orchestrator │ project_pipeline.py │ epf_tools.py        │
     │ workflows.py │ pipeline_*.py       │                     │
     └───────┬──────┴──────────┬──────────┴──────────┬──────────┘
             └───── задачи ────┼─────────────────────┘
                               │
            ┌──────────────────▼─────────────────┐
            │ очередь задач (SQLite) → worker.py │  ядро
            │ провайдеры, права, guard           │
            │ (config.py, guard.py) → процесс    │
            │ CLI агента (process_tree.py,       │
            │ herdr_exec.py, remote.py)          │
            └────────────────────────────────────┘
```

## Ядро

| Модуль | Что делает |
|---|---|
| `db.py` | вся SQLite: схема и миграции, очередь задач, серии повторов, уведомления, настройки, хранилище workflow и состояние конвейера (аренды целей, бюджет GitHub API). WAL, `_connect(immediate=True)` для «прочитал — решил — записал» |
| `models.py` | Pydantic-модели задач и workflow |
| `config.py` | `.env`, провайдеры (встроенные + `providers.json`), `build_cmd` — команда запуска CLI с параметрами задачи (`skip_permissions`, модель, effort, сессия) |
| `worker.py` | цикл воркера: взять задачу, собрать промпт, запустить процесс, дождаться, записать итог (`ИТОГ: …`), повторы и rate limit, heartbeat, восстановление зависших |
| `process_tree.py` | процесс задачи в своём Job Object (Windows) / группе: таймаут и отмена гасят всё дерево |
| `guard.py` | PreToolUse-хук Claude: режет катастрофические команды у задач без диалога (`PP_GUARD`) |
| `herdr_exec.py`, `remote.py`, `worktree.py` | исполнение в живой herdr-сессии, на другой машине по SSH, в своём git worktree |
| `usage.py`, `version.py`, `tg_auth.py` | расход за окно лимита, проверка обновлений, авторизация Telegram по телефону |
| `entrypoint.py` | точка входа процесса: быстрый путь адаптера проекта без открытия базы |

**Жизненный цикл задачи:** `pending` → `running` → `completed` / `failed` /
`cancelled`, или `rate_limited` с возвратом в очередь. Гейт конвейера может
вернуть взятую задачу в `pending` с причиной (`defer_task`): это ожидание, а не
итог — попытка не тратится, и в учёт запусков оно не попадает. Попытка задачи
отличается по `started_at` (attempt fencing): итог старой попытки не перезапишет
новую. Повторяющиеся задачи — серии (`task_series`); следующее вхождение
создаётся после завершения предыдущего.

**Права задачи.** `skip_permissions` запускает CLI без диалога разрешений (у
Claude — `--dangerously-skip-permissions`). При `PP_GUARD=auto` такие задачи
идут под `guard`.

## Надстройки

**Workflow Orchestrator** (`workflows.py`, [спецификация](WORKFLOW_ORCHESTRATOR_SPEC.md),
[руководство](WORKFLOW_AUTOMATION_GUIDE.md)) — большая инженерная задача:
planner → этапы → для каждого раунды «исполнитель → deterministic gate →
независимый аудитор» до PASS.
- Состояние — строки `workflows`, `workflow_stages`, `workflow_rounds`, `workflow_runs`.
- Журнал `workflow_events` только дописывается, это закреплено триггером в базе.
- Переходы проверяются по `state_version`.
- Исполнитель и аудитор — обычные задачи очереди.
- Указание оператора (`human_input`) уходит в промпт следующего исполнителя и
  аудитора.
- Повторный запуск исполнителя *того же этапа* получает отчёт предыдущего
  запуска как историю, которую нужно сверить с Git (`<предыдущий-запуск-исполнителя>`,
  последние 12 000 символов). Новый этап его не получает.

**Конвейер проектов** — очереди работ по GitHub-проектам (onebase): профили,
стадии review/merge с арендами (leases), единый барьер, бюджет GitHub API,
отчёты.
- Модули: `project_pipeline.py` (`pp pipelinectl`), `pipeline_insights.py`,
  `pipeline_board.py`, `pipeline_watch.py`, `pipeline_item_holds.py`,
  `pipeline_errors.py`, `fallback_handoff.py`.
- Правила работы — [pipeline-operation-policy.md](pipeline-operation-policy.md).
- Живёт внутри воркера — см. точки подключения ниже.

**1С-обработки** (`epf_tools.py`, `/epf` в боте) — доработка внешних
обработок 1С: выгрузка, задача агенту, сборка.

**Сценарии в `scripts/`**:
- `inbox` (почта и заявки KT) и `oneservice` — отдельные программы поверх REST
  API;
- `pp-herdr-run` и `pp-ssh-run` — обёртки-провайдеры для исполнения в
  herdr-сессии и по SSH.

## Точки подключения конвейера к воркеру

Конвейер — единственная надстройка, которая участвует в *планировании*
очереди, а не только ставит задачи. Все вызовы идут из `worker.py`, только для
задач серии (`task.series_id`), в `try/except`. Без профилей конвейера они
ничего не делают, а сбой конвейера не останавливает обычную очередь.

| Где в воркере | Вызов `pipeline_insights` | Контракт |
|---|---|---|
| `_claim_next_task` | `worker_lane_policy()`, `worker_budget_fairness_policy()`, `worker_lane_rank(task, policy, busy)` | какую из готовых задач взять и в какой «полосе» |
| `_execute_task_body` до запуска | `dispatch_gate(task)` | `None` или `{"action": "defer" / "complete_empty" / "restrict_prompt", "reason", …}` — отложить, закрыть без агента, сузить промпт |
| `_execute_task_body` до запуска | `execution_route(task, prompt, working_dir, retain_budget=True)` | `{"action": "run" / "block" / "defer", "mode", …}` — допуск к исполнению, бюджет |
| `_execute_task_inner`, `finally` | `release_execution_admission()` | вернуть зарезервированный бюджет |
| `_notify_pipeline_completion`, итог `ГОТОВО` | `after_task_completed(task, verdict)` | разбудить зависимые стадии |
| `_pipeline_repeat_guard` | `_matching_queue(task)` | выключатель повторяющегося блокера |

Со стороны базы конвейер держит `pipeline_target_reservations` (их
освобождают `mark_*` задачи) и отметки удержаний (`pipeline_item_holds`).

Выносить эти вызовы в отдельный реестр хуков сейчас не стали: конвейер
активно развивается ровно в этих местах, а реестр был бы переименованием,
которое конфликтует с каждым изменением. Когда контракт устоится, таблица
выше и есть готовый протокол `TaskHooks`.

## Интерфейсы и процессы

| Процесс | Команда | Что делает |
|---|---|---|
| сервер | `pp server` | REST API (`api.py`, FastAPI) и Web UI (`static/index.html` — один файл); фоновый сэмплер снимков конвейера |
| воркер | `pp worker` | исполняет очередь (`PP_CONCURRENCY` задач одновременно, не больше одной на рабочее дерево) |
| бот | `pp bot` | Telegram (`bot.py`): задачи, уведомления, отчёты |
| трей | `pp` / `pp tray` | запускает и сторожит остальные (`tray.py`) |

`start.ps1` / `stop.ps1` делают то же без трея, `docker-compose.yml` — в
контейнерах. Все процессы делят одну базу `promptpilot.db` в `PP_DATA_DIR`
(по умолчанию `~/.promptpilot`). Общаются они через неё: очередь,
уведомления, флаги отмены.

## Границы доверия

- **API.**
  - Без `PP_API_TOKEN` `pp server` не станет слушать адрес вне loopback.
    Исключение — `PP_ALLOW_INSECURE_BIND=1` в контейнере, где границей служит
    публикация порта.
  - Изменяющий запрос, который браузер пометил `Sec-Fetch-Site: cross-site`,
    получает 403 в любом режиме.
  - С токеном — Bearer или Basic.
- **Задача.** Без диалога разрешений — только по `skip_permissions`, и тогда
  `guard` режет катастрофические команды. Процесс задачи изолирован своим
  деревом.
- **Текст извне** (письма, формы) приходит только через сценарии `scripts/`.
  Заявки KT принимаются только с формы сайта (проверка DKIM), а их триаж
  запускается отдельным провайдером в пустой папке (`KT_TRIAGE_DIR`).
- **Telegram.** Кнопки и команды — только авторизованным по телефону, в личном
  чате (`require_auth`).

## Тесты и сборка

- `pytest` — весь набор (`tests/`), с изолированной базой (`isolated_db`).
- Проверки интерфейса `tests/*.cjs` запускаются в Node вручную. Из pytest
  проверяется только синтаксис встроенного JavaScript.
- CI (`.github/workflows/test.yml`):
  - `lint` — ruff, класс pyflakes;
  - `pytest -q -W error` на Python 3.10 и 3.12, Linux и Windows.
- `pp.spec` / `build.ps1` — сборка `pp.exe` через PyInstaller.
